# What does it cost to make every function async?

A measurement in Swift, to inform the choice of async strategy for a new language: if every function
in the language is a coroutine, what does that cost on ordinary programs?

Method and caveats are below the numbers. Everything here is regenerated by `./run.py`; the tables
between the markers are written by the script, not by hand.

Swift's async on WebAssembly is a different proposition from Swift's async on x86-64:

- **Where the optimizer inlines the awaits away, cost is zero**, exactly as on native: `nbody`,
  `collision`, `ecs`, `matmul` are all within a few percent of the synchronous build.
- **Where it does not, the cost is catastrophic.** A non-inlinable async call costs **556 ns** on
  Wasm against 18 ns natively, a factor of 30. Recursive programs, whose calls cannot be inlined
  away, land between 43x (`astar`) and 111x (`parser`).
- **Naive recursion does not run at all.** `fib` dies with `Maximum call stack size exceeded`, in
  Chrome and in Wasmtime alike. The trap backtrace alternates the ramp function and its resume
  partial functions, which is the shape you get when a coroutine returns by *calling* its
  continuation instead of tail-calling it: the stack grows with the number of calls rather than with
  recursion depth.

The cause is that the WebAssembly target has no guaranteed tail calls in this configuration. Swift's
async lowering wants `musttail` at every suspension and resume; `-mtail-call` is not on by default,
and turning it on in Swift 6.3.3 produced a module Wasmtime rejects as malformed
(`type mismatch: expected i32 but nothing on stack`), so the tail-call path is not usable today.

For a language designing its own lowering this is a strong argument against porting a CPS-style
async ABI to WebAssembly unchanged, and in favour of a design where a suspending call is an ordinary
call and resumption re-enters a frame from a driver loop, which needs no tail calls at all.

## How the variants are built

Each benchmark is written once, in async form: every user-defined function carries `async`, every
call site carries `await`. `build.sh` then derives all variants mechanically from that one file, so
no variant can differ from another in anything but the calling convention:

| variant | transformation |
|---|---|
| `sync` | delete every ` async` and `await ` token |
| `async` | the source as written |
| `syncni` | `sync` plus `@inline(never)` on every function |
| `asyncni` | `async` plus `@inline(never)` on every function |
| `mainactor` | `async`, with the workload moved into `@main`'s MainActor-isolated entry point |

`@inline(never)` stands in for calls the optimizer cannot inline: separate compilation units,
indirect calls, functions too large to inline. It is a proxy, not a measurement of a particular
build configuration.

Every variant prints a checksum, and `run.py` refuses to report a benchmark whose variants disagree.

## Reading the numbers

The async penalty tracks one thing: **calls per unit of work**. Programs whose inner loop is
arithmetic over arrays pay nothing once inlining is allowed. Programs that call a small function per
element pay a few tens of percent to a few times. A function that only calls itself pays about 20x,
because there is no work to amortize the per-call cost against.

Inlining separates the two halves of the first table, and it matters more than async-ness does:
`particles` is over 12x slower in the *synchronous* variant when inlining is forbidden. Where the
optimizer can inline, an async call costs what a sync call costs, because the frame and the
suspension point disappear together.

The `mainactor` table isolates a cost that dwarfs everything else, and a precise condition for it.
When the workload runs in Swift's MainActor-isolated entry point *and* the async callee is inlined
into it, `nbody` runs about 50x slower than the identical workload in a detached task: the hot loop
ends in `jmp swift_task_switch` and each iteration costs about 2.2 microseconds instead of 20
nanoseconds. Prevent that inlining and the same program is 1.00x. Inlining an async function into an
actor-isolated caller turns the callee's suspension points into suspensions of the enclosing
actor-isolated task, and each resume then takes a full executor round trip instead of a
same-executor continuation.

Two things follow. The split calling convention is cheap; what the runtime does *at* the await point
is not, and a design where resuming is a plain call into a host-driven loop never enters this
regime. And a cost model that depends on inlining decisions this sharply is hard to reason about:
the same source is 1.00x or 50x depending on whether one callee was inlined.

## Caveats

- **This is an upper bound for a new language.** Swift's async is heavier than the minimum for
  reasons a new language need not share: frames are dynamically sized and reached through async
  function pointers so async signatures stay ABI-stable and resilient; frames come from a slab
  allocator owned by a task; the default executor is a thread pool; and every resume may hop
  executors. A monomorphizing compiler with no dynamic dispatch, no ABI-stability requirement,
  statically known frame sizes and a single-threaded host-driven executor can be materially cheaper
  per call.
- The transformation converts functions and methods only. Initializers, property accessors and every
  standard-library call stay synchronous, so a language in which *everything* suspends would pay
  more than this on standard-library-heavy code.
- One machine, one x86-64 CPU. The native numbers use a Swift 6.5-dev snapshot; the WebAssembly
  numbers use Swift 6.3.3, because a Wasm SDK only works with the exact toolchain version it was
  built for. The Wasm figures therefore compare against their own synchronous baseline, not against
  the native ones.
- The Wasm builds have no `@inline(never)` variants except `microcall` and `particles`, and the
  `mainactor` variants are native-only.
- The native toolchain is a development snapshot rather than a release build. Its runtime libraries
  show no debug assertions.
- The machine is a laptop on `powersave`/`balanced`; each result set records the governor, platform
  profile and maximum clock so runs taken under different power conditions can be compared. Re-running
  the whole suite after a charger change moved the headline per-call figure by under 3%.
- Timing is in-process around the workload only, so process startup and concurrency-runtime
  initialization are excluded.

## Reproducing

Requires a Swift toolchain (6.2 or newer), Python 3, and `taskset`.

```sh
./build.sh          # generate every variant and compile it
./run.py --reps 7   # measure, verify checksums, rewrite the tables above
```

`./run.py --reps 3 fib nbody` measures a subset. `--cpu N` picks the core to pin to. Set `SWIFTC` or
`FLAGS` to override the compiler or its flags. Expect a full run to take a few minutes, most of it in
the `asyncni` and `mainactor` variants.

Layout: `src/` benchmark sources, `gen/` generated variants, `bin/` binaries, `results.json` raw
numbers with the environment they were taken in.
