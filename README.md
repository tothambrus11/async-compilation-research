# Async compilation research

Background research and measurements gathered while planning the async strategy for
[Ferlium](https://github.com/enlightware/ferlium), a statically typed functional scripting language
for Rust hosts. Ferlium's issue #18 asks for async built on its inferred effect system, with
"colorless" functions. The two candidate designs are:

- **A** — compile every function as a coroutine, and
- **B** — Lucian Radu Teodorescu's `spawn`/`await` model with stackful coroutines and thread
  inversion, as designed for Hylo and implemented in
  [concore2full](https://github.com/hylo-lang/concore2full).

Two things live here. `research/` is a written synthesis of how exceptions, unwinding, panics and
coroutines are actually compiled, on native targets and on WebAssembly, with seven source-cited
memos behind it. `bench/` is a measurement of what option A costs, in Swift, because Swift is the
production language whose async lowering is closest to it.

## research/

[`async-background.md`](research/async-background.md) is the synthesis; the memos it draws on are in
[`research/memos/`](research/memos). Every claim carries a tag: **[V]** verified against a primary
source, **[PK]** prior knowledge not re-fetched, **[?]** unverified or sources disagree,
**[inference]** a conclusion drawn here rather than found in a source. Section 7 lists the places
where sources disagree.

Contents: native unwinding (Itanium two-phase, personality routines, LSDA, DWARF CFI, Windows
funclets, ARM EHABI, Cranelift's `try_call`); WebAssembly exception handling (the exnref design and
what shipped where); WebAssembly async (Asyncify, JSPI, the stack-switching proposal, WASI 0.3's
callback ABI); Swift's async ABI in detail, on native and on Wasm; colorless async and effect-typed
suspension (Koka, Kotlin, Zig's two eras, OCaml 5, wasm_of_ocaml); and Teodorescu's spawn/await
model.

Dated facts are as of 2026-09-04.

## bench/

[`bench/RESULTS.md`](bench/RESULTS.md) answers one question with numbers: if every function in a
language is a coroutine, what does that cost?

Each benchmark is written once in async form, with `async` on every function and `await` at every
call site; the synchronous variant is generated from the same file by deleting those two tokens, so
no variant can differ from another in anything but the calling convention. Variants that add
`@inline(never)` model calls the optimizer cannot inline, and a variant that moves the workload into
an actor-isolated entry point prices executor hops. Everything is regenerated by the scripts, and
every variant prints a checksum that the runner checks for agreement.

Headline results on x86-64: 1.0x to 4.2x on realistic programs, 21x on a function that only calls
itself, and zero wherever the optimizer can inline the await away. A non-inlinable async call costs
17.5 ns more than a synchronous one; a real suspension costs 342 ns. On `wasm32` in Chrome the same
sources behave differently: free where awaits inline away, 43x to 111x on recursive code, 556 ns per
non-inlinable async call, and a naive recursive benchmark traps with `Maximum call stack size
exceeded`, because Swift's async lowering needs guaranteed tail calls that the WebAssembly target
does not provide by default.

See [`bench/RESULTS.md`](bench/RESULTS.md) for the tables, the method, and the caveats, of which the
most important is that Swift's async is an upper bound for a new language: its frames are
dynamically sized for ABI stability, allocated from a per-task slab allocator, and its default
executor is a thread pool. A monomorphizing compiler with statically sized frames and a
host-driven single-threaded executor can be materially cheaper.

## Reproducing

```sh
cd bench
./build.sh          # generate every variant and compile it
./run.py --reps 7   # measure natively, verify checksums, rewrite the tables

cd wasm
./build.sh          # needs a Swift SDK for WebAssembly matching the toolchain
./run_chrome.py     # run in headless Chrome through a minimal WASI shim
```
