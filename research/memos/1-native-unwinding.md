# How exceptions, stack unwinding and panics are compiled to native code
### Research memo for the Ferlium native/WASM backend design

## 0. Executive summary

There are really only three implementation families:

| Family | Happy-path cost | Throw-path cost | Metadata | Who uses it |
|---|---|---|---|---|
| **Table-based ("zero-cost") unwinding** | none in instruction stream; binary size + cache effects | very high (µs per throw, global lock in libgcc, table walks) | `.eh_frame`/CFI + LSDA, or `.pdata/.xdata`, or EHABI, or compact unwind | C++ (Itanium & MSVC), Rust panics, Wasmtime/Cranelift wasm-EH, .NET, Swift *for stack traces only* |
| **Register/flag checks (explicit propagation)** | a test+branch after each fallible call; error slot in a register | a return | none | Swift `throws`, Rust `Result`/`?`, Zig error unions, Go `error`, Midori checked exceptions, Herb Sutter's P0709 |
| **setjmp/longjmp** | save all callee-saved regs (+ maybe sigmask) at every `try`/frame registration | cheap-ish | none (or a runtime chain) | old GCC SJLJ EH, MinGW-32, Lua, many C libraries |

Rust's model ("values for errors, unwinding for panics") is the hybrid that most new languages converge on, and it is the one that fits an LLVM or Cranelift backend with the least engineering. Details and citations follow.

## 1. Table-based ("zero-cost") unwinding: the Itanium C++ ABI

### 1.1 Layering and the two-phase protocol
The Itanium C++ ABI EH spec is layered: "the base ABI, interfaces common to all languages and implementations; the C++ ABI, interfaces necessary for interoperability of C++ implementations; and the specification of a particular runtime implementation" ([Itanium C++ ABI: Exception Handling](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)). Level I (the "base ABI") is what Rust, Swift, Cranelift/cg_clif etc. reuse; it is implemented by `libgcc_s` (`_Unwind_*`) or LLVM `libunwind`.

A throw calls `__cxa_throw`, which "initiates unwinding via `_Unwind_RaiseException`, which never returns, unless an error condition is found" ([abi-eh](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)). `_Unwind_RaiseException` is two-phase:

- **Search phase**: the unwinder "repeatedly calls the personality routine, with the `_UA_SEARCH_PHASE` flag… until the personality routine reports either success (a handler found) or failure (no handler) in all frames." Nothing is modified; the stack is only *virtually* unwound.
- **Cleanup phase**: "the framework restarts in the cleanup phase… repeatedly calls the personality routine, with the `_UA_CLEANUP_PHASE` flag… until it gets to the frame with an identified handler" (`_UA_HANDLER_FRAME`). Each frame's landing pad runs destructors and then calls `_Unwind_Resume`, which "allows resumption of an existing exception… after executing cleanup code in a partially unwound stack" ([abi-eh](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)).

Why two phases? So that an uncaught exception can call `std::terminate` with the *original* stack intact (useful for core dumps), and so that debuggers can break at the throw point before any destructors run. `_Unwind_ForcedUnwind` (flag `_UA_FORCE_UNWIND`) is a one-phase variant driven by "an external agent" such as `longjmp_unwind` or pthread cancellation, where "no language is allowed to 'catch' the exception" ([abi-eh](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)).

The exception object carries a `_Unwind_Exception` header whose "`exception_class` field is a language- and implementation-specific identifier" (for C++ "the low four bytes are C++\0") — this is how Rust's personality recognises foreign exceptions ([abi-eh](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)).

### 1.2 Personality routines
The personality routine is "basically the bridge between the C++ exception library and the language-agnostic unwind library" ([MaskRay, C++ exception handling ABI](https://maskray.me/blog/2020-12-12-c++-exception-handling-abi)). GCC/Clang use `__gxx_personality_v0`; Rust uses `rust_eh_personality`. Rust's own doc comment describes the same protocol: in the search phase the personality is asked "to decide whether it should be caught at that stack frame"; in the cleanup phase "control is transferred to a special branch in the function body, the 'landing pad', which invokes destructors, frees memory, etc." ([rust/library/std/src/sys/personality/gcc.rs](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/personality/gcc.rs)). In phase 2 `__gxx_personality_v0` caches phase-1 results: when called with `_UA_HANDLER_FRAME` it "loads the cache and there is no need to parse `.gcc_except_table`" ([MaskRay](https://maskray.me/blog/2020-12-12-c++-exception-handling-abi)).

### 1.3 The LSDA (`.gcc_except_table`)
Each function's language-specific data area has a header (LPStart/TType encodings, call-site table length) followed by three tables ([MaskRay](https://maskray.me/blog/2020-12-12-c++-exception-handling-abi)):

- **Call-site table**: maps PC ranges to landing pads. "Each call site record has two values besides call site offset and length: landing pad offset and action record offset."
- **Action table**: a singly-linked chain; "Each action record has two values: switch value (SLEB128)… offset to the next action record: 0 indicates there is no next action record."
- **Type table**: `typeinfo` pointers for `catch` clauses, indexed by positive switch values (negative values denote exception specifications).

Two size notes from the same source: pre-Clang-12 "monolithic `.gcc_except_table` sections cannot be garbage collected by the linker" (fragmenting per function fixes that), and "Clang generates conservative code for a catch-all clause" assuming throwing destructors, which inflates size.

### 1.4 `.eh_frame` / DWARF CFI, `.eh_frame_hdr`
The unwinder needs to restore registers frame by frame without frame pointers. `.eh_frame` "comprises Common Information Entries (CIEs) and Frame Description Entries (FDEs). The CIE defines shared parameters like code alignment factors and return address registers, while FDEs describe specific function unwind behavior through bytecode-style instructions" (`DW_CFA_*` ops that define the Canonical Frame Address and where each callee-saved register lives) ([MaskRay, Stack unwinding](https://maskray.me/blog/2020-11-08-stack-unwinding)). `.eh_frame_hdr` (exposed via the `PT_GNU_EH_FRAME` program header) provides "a binary search index table describing (initial_location, FDE address) pairs" so FDE lookup is O(log n) rather than a linear scan ([MaskRay](https://maskray.me/blog/2020-11-08-stack-unwinding)). GCC distinguishes `-funwind-tables` (synchronous, correct only at call sites) from `-fasynchronous-unwind-tables` (correct at every instruction, needed for profilers and signal handlers).

### 1.5 LLVM IR: `invoke`/`landingpad`/`resume`
In LLVM IR a call that may unwind is an `invoke` with "two potential continuation points: where to continue when the call succeeds normally, and where to continue if the call raises an exception." The landing pad block begins with `landingpad`, which yields "a pointer and integer pair corresponding to the pointer to the exception structure and the selector value respectively"; if the frame cannot handle the exception it executes `resume`, which passes "in the result of the landingpad instruction for the original landing pad" ([LLVM ExceptionHandling](https://llvm.org/docs/ExceptionHandling.html)). The backend synthesises the LSDA and CFI from these plus the function's `personality` attribute. Functions marked `nounwind` need no `invoke` at call sites; this attribute is what `panic=abort` exploits (see §6).

### 1.6 libunwind vs libgcc_s
On glibc Linux the default level-I implementation is `libgcc_s.so.1` (`_Unwind_*`); LLVM's `libunwind` is an ABI-compatible replacement used on Apple, FreeBSD, Android and Fuchsia; the older nongnu "libunwind" is a *different* project mostly used for backtraces ([MaskRay](https://maskray.me/blog/2020-11-08-stack-unwinding)). Any language whose object files carry `.eh_frame` + an LSDA and register a personality can throw through, and be unwound by, either library — which is exactly what Rust does.

### 1.7 Cost model
- **Happy path**: no instructions are executed; the ABI's stated goal is to avoid "performing checkpointing tasks, such as saving the current pc or register state" during normal execution ([LLVM ExceptionHandling](https://llvm.org/docs/ExceptionHandling.html)). But Swift's designers point out that "zero-cost" is "something of a misnomer, because it does have several costs that can affect non-error performance," namely load-time work, decreased code locality and increased binary size ([Swift ErrorHandlingRationale](https://github.com/swiftlang/swift/blob/main/docs/ErrorHandlingRationale.md)). Optimisation constraints are real: every `invoke` ends a basic block, values live across it must be materialised in memory for the landing pad, and inlining of `invoke`d callees must merge cleanup chains.
- **Throw path**: a measured throw+catch of a trivial exception costs ~1.1 µs at `-O2` versus ~11 ns for an error-code return on a 2015 MacBook Pro, and the author notes "speed will decrease linearly with the depth of the call stack" ([Nutrient blog](https://www.nutrient.io/blog/performance-overhead-of-exceptions-in-cpp/)). **Flag**: the "1-2 µs *per frame*" figure you cited is not something I could verify; the sources I found give ~1-2 µs *per shallow throw/catch* plus a linear per-frame component (FDE lookup + CFI interpretation + personality call ×2).
- **Global lock**: in libgcc the FDE lookup calls `dl_iterate_phdr`, which takes glibc's `dl_load_write_lock`; "The unwinder grabs a global mutex to protect the unwinding tables from concurrent changes from shared libraries. This has disastrous performance implications on today's and upcoming machines" ([P2544R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2544r0.html)). Their numbers: on a 12-thread Ryzen a 10 % failure rate went from 19 ms to 247 ms; on a 128-core EPYC "we start to get performance problems already at 0.1% failure rate" and it is "unusable at 1% failure rate or more" ([P2544R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2544r0.html)). Seastar hit the same wall ([seastar#399](https://github.com/scylladb/seastar/issues/399)), and ScyllaDB worked around it because it "doesn't use dynamic libraries" ([ScyllaDB blog](https://www.scylladb.com/2024/05/14/better-goodput-performance-through-c-exception-handling/)). Neumann's prototype lock-free B-tree lookup restored near-linear scaling ([P2544R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2544r0.html)).
- **Binary size**: for the Facebook Android app, `.eh_frame_hdr + .eh_frame + .gcc_except_table` was **14.7 %** of aarch64 native library size, versus 6.1 % for ARM EHABI on armv7 ([MaskRay, Stack unwinding](https://maskray.me/blog/2020-11-08-stack-unwinding)). MinGW documentation puts DW2's code-size penalty at "< 10%" for typical applications ([Qt wiki MinGW-64-bit](https://wiki.qt.io/MinGW-64-bit)).

## 2. SJLJ exceptions and setjmp/longjmp

GCC's SJLJ scheme registers each frame that has cleanups/handlers in a thread-local chain at function entry (`_Unwind_SjLj_Register`) using a `setjmp`-like buffer; a throw walks the chain and `longjmp`s. LLVM still supports it via `llvm.eh.sjlj.setjmp`/`longjmp`, and its docs are blunt: the mechanism "results in faster exception handling at the expense of slower execution when no exceptions are thrown," so it is "less preferable than DWARF-based approaches" ([LLVM ExceptionHandling](https://llvm.org/docs/ExceptionHandling.html)). MinGW's comparison: DW2 "incurs no runtime overhead until an exception is thrown," whereas SJLJ "incurs a minor performance penalty (~15% in exception heavy code)" even when nothing is thrown; SJLJ's advantage is that it can unwind through foreign frames such as "windows callbacks" ([Qt wiki](https://wiki.qt.io/MinGW-64-bit)). Fedora dropped SJLJ for its mingw32 toolchain in favour of DW2 ([Fedora change](https://fedoraproject.org/wiki/Changes/Mingw32GccDwarf2)).

Raw `setjmp`/`longjmp` as a poor-man's exception mechanism (Lua, libpng, libjpeg) has the same cost profile: `setjmp` "saves… the stack pointer, the instruction pointer, possibly the values of other registers and the signal mask"; in practice "all non-volatile registers are saved to memory regardless of whether they are live," and `sigsetjmp(…, 1)` adds a `sigprocmask` syscall ([setjmp(3)](https://man7.org/linux/man-pages/man3/setjmp.3.html)). It runs no destructors, so it is incompatible with RAII/Drop unless every frame is a "plain old frame" — which is exactly why Rust's RFC 2945 defines forced unwinding over frames with destructors as UB (§6).

## 3. Windows: SEH, x64 tables and funclets

x64 Windows is also table-based, but with its own format. "Table-based exception handling requires a table entry for all functions that allocate stack space or call another function"; each `RUNTIME_FUNCTION` (start, end, unwind-info RVA) lives in `.pdata`, points at an `UNWIND_INFO` in `.xdata` containing prolog size, frame register and an array of `UNWIND_CODE`s (`UWOP_PUSH_NONVOL`, `UWOP_ALLOC_*`, `UWOP_SET_FPREG`, …) that describe the prolog; JITs must call `RtlAddFunctionTable`/`RtlInstallFunctionTableCallback` or get "unreliable exception handling and debugging" ([Microsoft: x64 exception handling](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64)). Unlike DWARF CFI, the unwinder also *disassembles epilogs*: "If the RIP is within an epilog… the code stream from RIP onward is examined." If the entry has `UNW_FLAG_EHANDLER`/`UNW_FLAG_UHANDLER`, the OS calls a language-specific handler with `(ExceptionRecord, EstablisherFrame, ContextRecord, DispatcherContext)`; the C handler is `__C_specific_handler`, the C++ ones are `__CxxFrameHandler3`/`4`. Dispatch is again two-pass (search, then unwind) ([Microsoft](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64)). `__CxxFrameHandler4` compresses the C++ metadata so it is "~60% smaller than the existing implementation, resulting in overall binary reduction of up to 20% for programs with heavy usage of C++ exception handling" ([MSVC blog](https://devblogs.microsoft.com/cppblog/making-cpp-exception-handling-smaller-x64/)).

**Why LLVM has a separate EH IR for MSVC.** On Itanium the catch block runs *after* the stack has been cut back to the handler frame. On Windows "the exception object is allocated in a child stack frame of the function handling the exception," so handlers must run *before* the stack is popped, as **funclets** — "special code regions callable with preserved parent frame context" that access "local variables in memory through the frame pointer, and returning some appropriate value, continuing the EH process" ([LLVM ExceptionHandling](https://llvm.org/docs/ExceptionHandling.html)). Hence `catchswitch`/`catchpad`/`catchret`/`cleanuppad`/`cleanupret`: "The catchpad and cleanuppad instructions establish new funclets," and "the EH tables for personalities that use funclets make implicit use of the funclet nesting relationship… and so are constrained in the set of funclet transitions they can represent" ([LLVM 18 docs](https://releases.llvm.org/18.1.8/docs/ExceptionHandling.html)). The CLR uses the same shape: managed handlers "are extracted into their own 'funclets'," which "to the OS… are treated just like first class functions (separate PDATA and XDATA)," with filters run in the first pass and non-volatile registers restored for second-pass funclets ([CoreCLR clr-abi.md](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/clr-abi.md)). Practical consequence for a new language: Cranelift only implements landingpad-style EH, so "cg_clif doesn't support unwinding on Windows" ([bjorn3, June 2025](https://bjorn3.github.io/2025/06/30/progress-report-june-2025.html)).

## 4. ARM EHABI and Apple compact unwind

**ARM EHABI (32-bit).** Unwind info is split into an index (`.ARM.exidx`, sorted by function address for binary search) and a table (`.ARM.extab`) with "one entry for each non-leaf function that may need to be unwound." Bit 31 selects the *compact model*, where "Bits 24-27 select one of 16 personality routines defined by the run-time support code" (`__aeabi_unwind_cpp_pr0/1/2`) and the unwind instructions are a byte-coded VM inlined into the index word; the *generic model* stores a personality pointer. It is still two-phase: "In phase 1, the stack is virtually unwound looking for a propagation barrier… In phase 2, the stack is really unwound and cleanups are run" ([ARM EHABI32](https://github.com/ARM-software/abi-aa/blob/main/ehabi32/ehabi32.rst)). MaskRay's equivalence: `.ARM.exidx` ≈ an enhanced `.eh_frame_hdr`, `.ARM.extab` ≈ `.eh_frame` + `.gcc_except_table` ([MaskRay](https://maskray.me/blog/2020-11-08-stack-unwinding)); the size benefit was quoted in §1.7. Rust's personality has an EHABI variant ([gcc.rs](https://github.com/rust-lang/rust/blob/master/library/std/src/sys/personality/gcc.rs)).

**Apple `__unwind_info`.** Each function gets a single 32-bit opcode: "Top 8 bits: metadata (function start flag, LSDA presence, personality index, opcode kind); lower 24 bits: architecture-specific instructions," in frame-based, frameless (immediate/indirect stack size) or DWARF-fallback modes, arranged in a two-level page table ([Faultlore, compact unwinding](https://faultlore.com/blah/compact-unwinding/)). `__unwind_info` and `__eh_frame` are complementary: `__eh_frame` "only includes FDEs for functions whose unwinding info cannot be represented in `__unwind_info`" ([MaskRay](https://maskray.me/blog/2020-11-08-stack-unwinding)). The trade-off is precision: "functions will generally have incorrect instructions for the function's prologue… and epilogue," and it "cannot reliably handle asynchronous unwinding when shrink wrapping or tail duplication occurs" ([Faultlore](https://faultlore.com/blah/compact-unwinding/); [MaskRay](https://maskray.me/blog/2020-11-08-stack-unwinding)). AArch64's ABI never adopted a compact format ([abi-aa#344](https://github.com/ARM-software/abi-aa/issues/344)); a 2025 "ELF compact unwind" prototype "reduces VM size by 4.5-6.1% compared to frame pointers" with "only 6.36% of FDEs" needing the full CFI encoding ([MaskRay 2025](https://maskray.me/blog/2025-10-26-stack-walking-space-and-time-trade-offs)).

## 5. Alternative: explicit error returns

**Swift `throws`.** Swift does not unwind for `throws`. The error is returned in a dedicated register — `r12` on x86-64, `x21` on arm64 — chosen "because they're normally callee-saved registers, so a non-throwing function can be 'toll-free bridged' as a throwing one, since the non-throwing ABI will always preserve null in the error register" (Joe Groff, quoted in [mikeash](https://www.mikeash.com/pyblog/friday-qa-2017-08-25-swift-error-handling-implementation.html)). The caller emits `test r12, r12; jne <catch>` after every throwing call — "one instruction… to jump-if-not-zero into the catch block" ([mikeash](https://www.mikeash.com/pyblog/friday-qa-2017-08-25-swift-error-handling-implementation.html)). LLVM exposes this as the `swifterror` parameter attribute. The rationale document classifies errors into simple domain errors (→ `Optional`), recoverable errors (→ `throws`), universal errors and logic failures, and says of the last: "the failure should be handled by fixing the code, not by attempting to recover dynamically" ([ErrorHandlingRationale](https://github.com/swiftlang/swift/blob/main/docs/ErrorHandlingRationale.md)). Note that the ABI whitepaper itself still says the calling-convention details "aren't yet settled" ([CallingConvention.rst](https://github.com/swiftlang/swift/blob/main/docs/ABI/CallingConvention.rst)); the register assignment is verified from mikeash/Groff, not from the whitepaper.

**Rust `Result` + `?`.** `?` desugars to a match and early return; there is no unwinding, and the Nomicon ranks it first: `Option`/`Result` for recoverable errors, panics only "for programming errors or *extreme* problems" ([Nomicon: Unwinding](https://doc.rust-lang.org/nomicon/unwinding.html)).

**Zig.** "Each error is an unsigned integer with a maximum bit-width of 16"; `!T` is a tagged union; `errdefer` runs cleanup only on error return; *error return traces* record the propagation path but are "only generated in Debug and ReleaseSafe modes" ([Zig docs](https://ziglang.org/documentation/master/)). This is a neat answer to the "values lose the stack trace" objection.

**Go.** `error` is an ordinary return value (multiple returns); `panic` is the unwinding path (§6).

**Midori.** Two-pronged: "All bugs detected at runtime caused something called abandonment, which was Midori's term for… fail-fast," while recoverable errors used statically checked exceptions with "deep type system support to aid checking and verification." Duffy argues exceptions "get error handling code and data off hot paths which increases I-cache and TLB performance" ([Duffy, The Error Model](https://joeduffyblog.com/2016/02/07/the-error-model/)). **Flag**: I could not confirm from the fetched text exactly which codegen (tables vs. return-code-like) Midori used for checked exceptions.

**P0709 "Zero-overhead deterministic exceptions."** Sutter proposes `throws` functions that return a two-pointer `std::error` via the normal return path (effectively a discriminated return checked by the caller), motivated by the fact that projects disabling exceptions "are therefore not actually using Standard C++, but using a divergent language dialect" ([P0709R4](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2019/p0709r4.pdf)). P2544 measured a C++ emulation of this at ~25 % overhead vs ~10 % for a hand-written assembler version, with `std::expected` "over 4× slower in worst-case scenarios" under heavy failure rates ([P2544R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2544r0.html)). Boost.Outcome ships a simulation ([Boost.Outcome experimental](https://boostorg.github.io/outcome/experimental.html)).

**Khalil Estell (2024-25).** On a Cortex-M4 with GCC he "explores the space cost of exceptions… compares it to result types, identifying the point where result types become more costly in terms of code size than exceptions" — i.e. past a certain number of propagation sites, the per-call-site `if (err) return err;` code outweighs the one-time unwinder + tables ([ACCU 2024 session](https://accuconference.org/2024/session/reducing-binary-sizes-in-embedded-systems-using-cpp-exceptions); [CppCon 2024 keynote](https://cppcon.org/2024-keynote-khalil-estell/)). His 2025 follow-up reports "+90% performance improvement" by replacing O(log n) table lookups with O(1) data-oriented layouts within the fixed ABI ([isocpp 2025](https://isocpp.org/blog/2025/08/cppcon-2025-cutting-cpp-exception-time-by-93.4-khalil-estell)). **Flag**: I could not obtain the exact crossover numbers from the slides.

## 6. Panics

### Rust
- **Strategies.** `-C panic=unwind|abort|immediate-abort`; "If any crate in the crate graph uses `abort`, the final binary… must also use `abort`" ([rustc codegen options](https://doc.rust-lang.org/rustc/codegen-options/index.html)). With abort "the optimizer may assume that unwinding across Rust frames is impossible, which can result in both code-size and runtime speed improvements" ([Reference: Panic](https://doc.rust-lang.org/reference/panic.html)) — concretely, calls become `nounwind`, `invoke` becomes `call`, landing pads and LSDAs vanish. `-C force-unwind-tables` keeps `.eh_frame` for backtraces even with abort ([codegen options](https://doc.rust-lang.org/rustc/codegen-options/index.html)).
- **Cost philosophy.** "If a program doesn't unwind, there should be no runtime cost for the program being *ready* to unwind. As a consequence, actually unwinding will be more expensive than in e.g. Java" ([Nomicon](https://doc.rust-lang.org/nomicon/unwinding.html)).
- **`catch_unwind`.** Requires `UnwindSafe` (bypassable with `AssertUnwindSafe`); "only catches unwinding panics, not those that abort the process"; "not recommended… for a general try/catch mechanism"; and dropping the `Err` payload "may in turn panic!" ([std::panic::catch_unwind](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html)).
- **Double panic / panic in Drop.** "`drop()` may itself be called during unwinding due to a panic, and if the `drop()` panics in that situation (a 'double panic'), this will likely abort the program" ([Drop docs](https://doc.rust-lang.org/std/ops/trait.Drop.html)).
- **FFI / RFC 2945.** Rust `extern "C"` functions get an abort shim: "`panic!` will cause an `abort` if it would otherwise 'escape' from a function defined with `extern "C"`"; `extern "C-unwind"` permits unwinding in both directions. The RFC's table: with `panic=unwind`, `"C-unwind"` unwinds for both Rust and foreign exceptions; `"C"` aborts on Rust panics and is UB for foreign unwinds; with `panic=abort` `"C-unwind"` aborts and `"C"` is still UB for foreign unwinds. Forced unwinding (`longjmp`, cancellation) over a frame with destructors is UB; over a "plain old frame" is (for now) unspecified. Design invariant: "Changing from `panic=unwind` to `panic=abort` cannot cause undefined behavior" ([RFC 2945](https://rust-lang.github.io/rfcs/2945-c-unwind-abi.html); [Reference](https://doc.rust-lang.org/reference/panic.html)).
- **WASM.** `wasm32-unknown-unknown` "is compiled with `-Cpanic=abort` by default"; "since mid-2025 the WebAssembly `exception-handling` proposal reached stabilization… it's possible to enable `-Cpanic=unwind` on wasm targets" but only with `-Zbuild-std` and (since 2025-10) `-Cllvm-args=-wasm-use-legacy-eh=false` ([rustc book](https://doc.rust-lang.org/beta/rustc/platform-support/wasm32-unknown-unknown.html)). Emscripten targets enable `-fwasm-exceptions` by default ([rustc book: emscripten](https://doc.rust-lang.org/beta/rustc/platform-support/wasm32-unknown-emscripten.html)).

### Go
`panic()` compiles to `runtime.gopanic`, which builds a `_panic` record and iterates deferred calls; Go has "two different ways of doing defers": heap/stack-linked `_defer` records and *open-coded* defers where "we simply store the defer function/arg information into specific stack slots" guarded by a `deferBits` mask; during a panic `nextFrame` uses the runtime `unwinder` to scan frames and reads per-function `funcdata` to find open-coded defers ([runtime/panic.go](https://go.dev/src/runtime/panic.go); [open-coded defers proposal](https://go.googlesource.com/proposal/+/refs/heads/master/design/34481-opencoded-defers.md)). The stack walker uses `pclntab` to map PC → function/frame size ([Go runtime stacktraces](https://internals-for-interns.com/posts/go-runtime-stacktraces/)). `recover` requires "exactly one non-wrapper frame between gopanic and gorecover"; recovery `mcall`s into `recovery()`, which resets `sp`/`pc` to the deferring function's `deferreturn` and `gogo`s; a "panic during panic" is printed and the process exits ([panic.go](https://go.dev/src/runtime/panic.go)). There is no LSDA and no personality: the compiler's own metadata plus a runtime-controlled stack layout do the job — an option only available when you control the whole ABI and never interoperate with C frames mid-unwind.

### Swift, Zig, JVM, .NET
- Swift `fatalError`/precondition failures compile to `Builtin.int_trap()`, i.e. `ud2` on x86-64 (`brk` on arm64) ([cocoawithlove](https://www.cocoawithlove.com/blog/2016/02/02/partial-functions-part-two-catching-precondition-failures.html); [Assert.swift](https://github.com/swiftlang/swift/blob/a05cd35a7f8e3cc70e0666bc34b5056a543eafd4/stdlib/public/core/Assert.swift)). No unwinding, no destructors.
- Zig `@panic` calls the (overridable) panic handler, which prints a stack trace and traps/aborts ([Zig docs](https://ziglang.org/documentation/master/)).
- JVM bytecode carries a per-method `exception_table` of `{start_pc, end_pc, handler_pc, catch_type}` searched in order on `athrow` ([JVMS §4.7.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.7.3); [foojay](https://foojay.io/today/how-jvm-handles-exceptions/)) — **flag**: I cite the anchor but could not fetch the exact wording. JIT-compiled code keeps equivalent PC-range tables.
- .NET is two-pass with funclets on x64/arm64 (§3); filters run in pass 1, finally/catch in pass 2 ([CLR Inside Out](https://learn.microsoft.com/en-us/archive/msdn-magazine/2009/february/clr-inside-out-handling-corrupted-state-exceptions); [clr-abi.md](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/clr-abi.md)).

## 7. Unwinding vs. destructors, RAII and coroutines/async

**RAII/Drop.** Table-based unwinding runs destructors from landing pads during phase 2 — "as if every function instantly returned" ([Nomicon](https://doc.rust-lang.org/nomicon/unwinding.html)). Explicit-return schemes run them via ordinary early-return paths; `errdefer` in Zig is the explicit analogue. `longjmp` runs none, which is the source of RFC 2945's UB rules.

**C++20 coroutines.** The compiler wraps the body in an implicit `try { … } catch (...) { promise.unhandled_exception(); }`, called "while the exception is still active" so the promise can `current_exception()` it into the return object; the coroutine frame is not unwound *through* — the exception is converted to a value at the coroutine boundary. Exceptions escaping `initial_suspend`, `final_suspend` or `unhandled_exception` itself are unwound through the ramp/resumer and, in the latter case, hit `std::terminate` because it "is treated the same as an exception being thrown during stack-unwinding" ([Old New Thing](https://devblogs.microsoft.com/oldnewthing/20210401-00/?p=105043); [Lewis Baker](https://lewissbaker.github.io/2020/05/11/understanding_symmetric_transfer); [coroutines-ts#17](https://github.com/GorNishanov/coroutines-ts/issues/17); standard text at [dcl.fct.def.coroutine](https://eel.is/c++draft/dcl.fct.def.coroutine) — not re-fetched here). In LLVM, `llvm.coro.end(ptr, i1 true, …)` marks the unwind path; "In the unwind path… `coro.end` will mark the coroutine as done, making it undefined behavior to resume the coroutine again," and on WinEH the frontend must attach a funclet bundle to it ([LLVM Coroutines](https://llvm.org/docs/Coroutines.html)).

**Rust async.** A `Future` is a plain state-machine struct and `poll` is a plain function, so a panic in an `.await`ed body unwinds out of `poll` like any other call; the state machine's `Drop` then drops locals held across await points. Executors decide policy: Tokio catches panics per task ("The panic is forwarded to the task's `JoinHandle` and all spawned tasks continue running normally" under the default `UnhandledPanic::Ignore`, or `ShutdownRuntime`) and exposes `JoinError::is_panic`/`into_panic` for `resume_unwind` ([tokio UnhandledPanic](https://docs.rs/tokio/latest/tokio/runtime/enum.UnhandledPanic.html); [tokio JoinError](https://docs.rs/tokio/latest/tokio/task/struct.JoinError.html)). Nothing special is needed in the codegen — which is a strong argument for the poll/state-machine design if Ferlium's async will coexist with panics.

## 8. Frame pointers, CFI-less unwinding, shadow stacks

Frame-pointer chains give a trivial O(1)-per-frame walk (`push rbp; mov rbp, rsp`), at the cost of a register and prologue overhead; LLVM's compile-time tracker shows enabling them costs "+2.44%" instructions but "just 0.56%" wall time, and on x86-64 `rbp`-relative addressing can even shrink code ([MaskRay 2025](https://maskray.me/blog/2025-10-26-stack-walking-space-and-time-trade-offs)). Fedora 38 and Ubuntu re-enabled them distribution-wide because perf's DWARF mode copies stacks: "DWARF's perf.data is over 10 times larger… collecting 10s of gigabytes of data for a single minute is not very practical" ([R. W. M. Jones](https://rwmj.wordpress.com/2023/02/14/frame-pointers-vs-dwarf-my-verdict/); [Fedora change](https://fedoraproject.org/wiki/Changes/fno-omit-frame-pointer); [Brendan Gregg](https://www.brendangregg.com/blog/2024-03-17/the-return-of-the-frame-pointers.html)). Limits: leaf functions, prolog/epilog windows, and code that omits them ([Red Hat](https://developers.redhat.com/articles/2024/10/30/limitations-frame-pointer-unwinding)). Newer formats — kernel ORC and userspace **SFrame** (kernel-side userspace unwinding merged for 6.17) — trade a ~10 % larger table (SFrame 8.87 MiB vs `.eh_frame`+hdr 8.06 MiB for clang) for simple, lock-free walking ([LWN](https://lwn.net/Articles/1029189/); [Oracle](https://blogs.oracle.com/linux/beyond-eh-frame-frame-pointers-the-technical-underpinnings-of-sframe); [MaskRay 2025](https://maskray.me/blog/2025-10-26-stack-walking-space-and-time-trade-offs)). Hardware shadow stacks (x86 CET, AArch64 GCS) "can be used to get stack traces" and may eventually displace metadata for *backtraces* ([MaskRay 2025](https://maskray.me/blog/2025-10-26-stack-walking-space-and-time-trade-offs)) — but not for *exception* unwinding, which must also restore callee-saved registers and locate landing pads. Wasmtime's design shows the pragmatic middle: mandate frame pointers, walk them yourself, and use compiler-emitted tables only for handler lookup ([Fallin](https://cfallin.org/blog/2025/11/06/exceptions/)).

## 9. Backend options for a new language (LLVM / Cranelift / WASM)

**Cranelift (verified).** Between March and August 2025 (37 PRs, ~16k lines; initial `try_call` PR [#10510](https://github.com/bytecodealliance/wasmtime/pull/10510), Wasm EH [#11326](https://github.com/bytecodealliance/wasmtime/pull/11326)) Cranelift gained `try_call`/`try_call_indirect`: a block terminator with an *exception table* whose handlers are ordinary blocks receiving payloads via block params; all registers are clobbered at the site, live values are spilled, and payloads travel in two registers "following Itanium convention… x0 and x1 on aarch64." Wasmtime's unwinder is one-phase, walks frame-pointer chains itself and resumes handlers with a small asm stub; uncaught exceptions become traps/`anyhow::Error` at the host boundary ([Fallin, Exceptions in Cranelift and Wasmtime](https://cfallin.org/blog/2025/11/06/exceptions/); [Bytecode Alliance](https://bytecodealliance.org/articles/wasmtime-exceptions)). Crucially for you, rustc's Cranelift backend proved the *other* integration: cg_clif emits `try_call` plus a GCC-compatible `.gcc_except_table` and uses the system `libgcc`/`libunwind` with `rust_eh_personality`, so its output interoperates with C++ unwinding on Linux; it is off by default (build-time regression), Windows is unsupported (funclets), macOS needs table-encoding tweaks ([Tweede golf](https://tweedegolf.nl/en/blog/157/exception-handling-in-rustc-codegen-cranelift); [bjorn3](https://bjorn3.github.io/2025/06/30/progress-report-june-2025.html)). Cranelift already emits SysV/Windows unwind info for backtraces.

**LLVM.** Full Itanium (`invoke`/`landingpad`/`resume` + personality), WinEH funclets, SJLJ and Wasm EH ([LLVM ExceptionHandling](https://llvm.org/docs/ExceptionHandling.html)). You must (a) write or reuse a personality (reusing `rust_eh_personality` semantics — cleanup-only landing pads plus a single "catch-all" intrinsic — is the minimal design), (b) emit `uwtable` so CFI is generated, (c) link `libgcc_s`/`libunwind`. CFI emission is essentially free (the backend derives it from prologue/epilogue); the LSDA is derived from `invoke` edges.

**WASM.** The EH proposal (`try_table`/`throw`/`throw_ref`) is stabilised and supported by LLVM, Wasmtime and browsers, but Rust still ships `panic=abort` on `wasm32-unknown-unknown` and legacy-vs-new EH encoding is a live compatibility issue ([rustc book](https://doc.rust-lang.org/beta/rustc/platform-support/wasm32-unknown-unknown.html)). A `Result`-based design needs nothing from the wasm EH proposal at all.

## 10. Design implications for Ferlium

Given: implemented in Rust, currently interpreted, targeting native (LLVM or Cranelift) and WASM, with async on the roadmap.

| Option | Happy-path cost | Error-path cost | Backend effort | WASM | Interop (C/Rust FFI) | Async/coroutines | Debuggability |
|---|---|---|---|---|---|---|---|
| **A. Errors as values (`Result`/error unions), panics = trap/abort** | one test+branch per fallible call; small code per site | a return | minimal — no personality, no LSDA, no unwinder; works identically in interpreter, Cranelift, LLVM, wasm | trivial | trivial (values cross FFI) | trivial (poll/state machine) | needs Zig-style error return traces or explicit context to recover "where did it fail" |
| **B. Errors as values, panics = table-based unwind (Rust model)** | as A, plus `.eh_frame`/LSDA size (~5-15 % of binary) and `invoke` optimisation barriers | µs-scale, lock-contended; acceptable because panics are rare | moderate: personality + LSDA emission + libunwind linkage (LLVM: standard; Cranelift: `try_call` + hand-emitted `.gcc_except_table`, Linux/macOS only) | requires wasm EH (`panic=unwind` style) or fall back to abort | must add "abort at `extern "C"` boundary" shims and a `C-unwind`-like ABI; `catch_unwind` semantics for foreign exceptions | panics propagate out of `poll`; executor may catch per task; drop of suspended frames on unwind | full backtraces via same tables; destructors run before abort → cleaner shutdown |
| **C. Exceptions (table-based) as the primary error mechanism (C++/Java style)** | none in instructions; large tables; locality loss | prohibitive for error rates ≳0.1-1 % on many-core machines (P2544) | as B plus type matching in personality, `catch` codegen, WinEH funclets for Windows | wasm EH mandatory | painful across C frames | must convert to value at coroutine boundary (C++ `unhandled_exception`) | good |
| **D. Swift-style register-carried errors** | 1 zeroing + 1 branch per throwing call | a return | needs custom calling convention (`swifterror` in LLVM; not in Cranelift) | no dedicated register; degrade to A | non-standard ABI at FFI | as A | as A |
| **E. setjmp/longjmp** | save all callee-saved regs per protected region | cheap | trivial in C, awkward in Rust-hosted runtime | not available | breaks RAII/Drop, UB across Rust frames | incompatible with suspended frames | poor |

Concrete recommendations:

1. **Adopt B, and make A a compiler mode.** Errors are typed values propagated by a `?`-like operator; panics are the only unwinding mechanism, with a `panic=abort`-style build mode that removes all EH machinery (this is also your WASM-first story). The invariant to preserve, borrowed verbatim from RFC 2945: switching unwind → abort must never introduce UB ([RFC 2945](https://rust-lang.github.io/rfcs/2945-c-unwind-abi.html)).
2. **Start with Cranelift + `try_call`, mirroring cg_clif** if you want a fast-compiling backend: emit cleanup-only landing pads, a Rust-compatible LSDA, and reuse `libgcc_s`/`libunwind` (you can literally link `rust_eh_personality` from std). Accept that Windows will be abort-only until Cranelift grows funclets ([bjorn3](https://bjorn3.github.io/2025/06/30/progress-report-june-2025.html)). Choose LLVM if Windows unwinding or WinEH interop is a launch requirement.
3. **Keep frame pointers on by default.** Cheap (≈0.5 % wall time), makes Wasmtime-style custom walking and profiler support possible, and lets you ship a small custom backtrace walker without depending on libunwind for diagnostics ([MaskRay 2025](https://maskray.me/blog/2025-10-26-stack-walking-space-and-time-trade-offs)).
4. **Define the FFI rules now**: `extern "C"` = abort-on-unwind shim; a separate `"C-unwind"` ABI if you ever need C++ exceptions to traverse Ferlium frames; forced unwinding over frames with destructors is UB.
5. **Async via poll/state machines, not stackful coroutines**: it makes panic propagation and frame destruction "just" ordinary unwinding through `poll` and lets the executor apply a per-task `catch_unwind` policy ([tokio](https://docs.rs/tokio/latest/tokio/runtime/enum.UnhandledPanic.html)). If you ever add a C++-style stackful/compiler-transformed coroutine, decide up front whether a panic in the body becomes a value at the boundary (C++ `unhandled_exception`) or unwinds the resumer.
6. **Recover diagnostics for value errors** with Zig-style error return traces in debug builds ([Zig docs](https://ziglang.org/documentation/master/)) — the most common practical complaint about value-based errors is losing the origin, and this solves it without unwinding.
7. **Do not expect "zero-cost" to be free**: budget ~5-15 % binary size for unwind tables when panics unwind ([MaskRay](https://maskray.me/blog/2020-11-08-stack-unwinding)), and never use panics for control flow: the libgcc global lock makes throw throughput collapse on many-core machines ([P2544R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2544r0.html)).
