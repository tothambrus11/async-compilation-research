## 2. How Swift async compiles to Wasm

### 2a. `musttail`/`swifttailcc` on the WebAssembly backend — the central question

Swift's IRGen picks the async calling convention per target:

```cpp
// lib/IRGen/IRGenModule.cpp
bool isAsyncCCSupported =
  clangASTContext.getTargetInfo().checkCallingConvention(clang::CC_SwiftAsync)
  == clang::TargetInfo::CCCR_OK;
if (isAsyncCCSupported) { SwiftAsyncCC = llvm::CallingConv::SwiftTail; AsyncTailCallKind = TCK_MustTail; }
else                    { SwiftAsyncCC = SwiftCC;                       AsyncTailCallKind = TCK_Tail; }
```
**[V]** ([IRGenModule.cpp](https://github.com/swiftlang/swift/blob/main/lib/IRGen/IRGenModule.cpp)). And in `GenCall.cpp`: "If target doesn't support musttail (e.g. WebAssembly), the function passed to coro.end.async can return control back to the caller. So use ret void instead of unreachable" **[V]** ([GenCall.cpp](https://github.com/swiftlang/swift/blob/main/lib/IRGen/GenCall.cpp)).

Clang's WebAssembly target now answers `CC_SwiftAsync` conditionally:

```cpp
case CC_SwiftAsync: return HasTailCall ? CCCR_OK : CCCR_Error;
```
**[V]** ([clang/lib/Basic/Targets/WebAssembly.h](https://github.com/llvm/llvm-project/blob/main/clang/lib/Basic/Targets/WebAssembly.h)). This is very recent: upstream LLVM [#188296 "Wasm: add support for `swifttailcc` calling convention"](https://github.com/llvm/llvm-project/pull/188296) merged 31 March 2026 and [#203330 "clang: enable `swiftasynccall` for Wasm"](https://github.com/llvm/llvm-project/pull/203330) merged 18 June 2026 ("`swiftasynccall` is lowered to Wasm `return_call` and `return_call_indirect` instructions when tail calls are enabled") **[V]**. The Swift fork merged the same in [swiftlang/llvm-project#12648](https://github.com/swiftlang/llvm-project/pull/12648) (18 June 2026), and [swift#88074](https://github.com/swiftlang/swift/pull/88074) (19 June 2026) added tests, closing [swift#69333 "Support `swifttailcc` on WebAssembly"](https://github.com/swiftlang/swift/issues/69333) (opened Oct 2023) **[V]**.

The test spells out the two regimes **[V]** ([test/IRGen/async_wasm_tailcall.swift](https://github.com/swiftlang/swift/blob/main/test/IRGen/async_wasm_tailcall.swift)):

- default (no flag): `define swiftcc void @"$s4test6callerSiyYaF"(ptr swiftasync …`, `NOTAIL-NOT: musttail call`, no `return_call` in assembly;
- with `-Xcc -mtail-call`: `swifttailcc`, `musttail call swifttailcc void`, and `return_call` in the `.s`.

So: **`-mtail-call` is not on by default in the Swift compiler**, and it isn't in LLVM's `generic` Wasm CPU either (`generic` = bulk-memory, call-indirect-overlong, multivalue, mutable-globals, nontrapping-fptoint, reference-types, sign-ext — no `tail-call`) **[V]** ([WebAssembly.td](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/WebAssembly/WebAssembly.td)). Whether the *shipped* 6.3.x SDK stdlib is compiled with tail calls I could not confirm; the stdlib build scripts I inspected (`wasistdlib.py`, `wasmstdlibhelpers.py`, `Runtime-WASI-wasm32.cmake`) contain no `tail-call` flag **[?]**, and the SwiftWasm tracking issue [#5568 "Tail-call calling convention"](https://github.com/swiftwasm/swift/issues/5568) (still open) lists as a blocker "We need to build separate stdlib builds for tail-call enabled and not, to allow produced binary to be used with WebAssembly runtimes with/without tail-call support" **[V]**. Since the two regimes use different LLVM calling conventions (`swiftcc` vs `swifttailcc`), mixing objects across the regimes is at minimum an ABI hazard **[?, inference]**. Practical conclusion: as of today, released Swift SDKs run async code *without* tail calls; the tail-call path is available in main snapshots by passing `-Xcc -mtail-call` (and probably requires a matching stdlib).

**What LLVM does with `musttail` without the feature.** `WebAssemblyTargetLowering::LowerCall` refuses to silently degrade a `musttail`: `if (!Subtarget->hasTailCall()) NoTail("WebAssembly 'tail-call' feature not enabled");` where `NoTail` calls `fail()` for must-tail calls and merely clears `IsTailCall` for ordinary `tail` calls. Other disqualifiers: varargs, mismatched caller/callee return types, and pointers to `alloca`s among the arguments ("WebAssembly does not support tail calling with stack arguments") **[V]** ([WebAssemblyISelLowering.cpp](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/WebAssembly/WebAssemblyISelLowering.cpp)). `CoroSplit` only marks the async resume call `musttail` when `TTI.supportsTailCallFor(...)` — for Wasm `supportsTailCalls()` returns `getST()->hasTailCall()` **[V]** ([CoroSplit.cpp](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Transforms/Coroutines/CoroSplit.cpp), [WebAssemblyTargetTransformInfo.cpp](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/WebAssembly/WebAssemblyTargetTransformInfo.cpp)). That check was added by Yuta Saito in [llvm#81481 "[Coro][WebAssembly] Add tail-call check for async lowering"](https://github.com/llvm/llvm-project/pull/81481) (Feb 2024) after a Swift stdlib build failed with "cannot guarantee tail call due to mismatched parameter counts" ([swiftwasm#5567](https://github.com/swiftwasm/swift/issues/5567)) **[V]**.

**Consequence without tail calls: unbounded stack growth.** In the non-tail regime each async→async call and each resume is a real Wasm `call`, so a CPU-bound `await` loop nests frames. [swiftwasm#5614 "Potential stack overflow while calling async functions in a loop"](https://github.com/swiftwasm/swift/issues/5614) (Nov 2025, Swift 6.1 SDK) reproduces with

```swift
func hello() async throws {}
for _ in 0..<500000 { try await hello() }
```
→ `wasm trap: call stack exhausted`, with a 6,000-deep backtrace alternating `swift_task_switch`, `$s2MT5helloyyYaKF`, and `main`'s partial functions (`…TQ1_`, `…TY2_`); Saito: "This is one of the major limitation of our Wasm target support. We still don't support tail-call yet" **[V]**. Earlier, [swiftwasm#5573](https://github.com/swiftwasm/swift/issues/5573) (Mar 2024) hit the same in XCTest suites; the workaround was `-Xlinker -z -Xlinker stack-size=1048576` plus `wasmtime --wasm max-wasm-stack=…` (one user needed 16 MiB) **[V]**. The mitigation that keeps most real apps working is that every *actual* suspension returns to the executor loop (the stack resets when a job ends), so only non-suspending await chains accumulate depth **[PK/inference]**.

**Engine support for tail calls.** V8 shipped Wasm tail calls in V8 v11.2 (Chrome 112, blog dated 6 April 2023) with Liftoff support ("they must be supported, or the baseline code might run out of stack space"); the blog explicitly ties them to symmetric transfer in C++20 coroutines and `-mtail-call` **[V]** ([v8.dev/blog/wasm-tail-call](https://v8.dev/blog/wasm-tail-call)). Tail calls became Baseline Newly available in all three engines on 11 December 2024 (Safari 18.2 was the last) **[V]** ([web.dev](https://web.dev/blog/wasmgc-wasm-tail-call-optimizations-baseline)); Firefox shipped in December 2023 (Firefox 121 per prior knowledge) **[PK]**. Tail calls are part of Wasm 3.0 (17 Sept 2025) **[V]** ([webassembly.org/news](https://webassembly.org/news/2025-09-17-wasm-3.0/)). Wasmtime enabled them by default in 21.0 (partially, bug) and for all configurations in 22.0 **[V]** ([wasmtime#8682](https://github.com/bytecodealliance/wasmtime/pull/8682)). Historic context: Leaning Technologies' 2020 "sad state of tail calls" post documented Liftoff not supporting them then and SpiderMonkey's ABI mismatch **[V]** ([labs.leaningtech.com](https://labs.leaningtech.com/blog/extreme-webassembly-2-the-sad-state-of-webassembly-tail-calls)).

### 2b. The async context "register" on a register-less target

On x86-64/arm64 the async context lives in r14/x22. On Wasm it is simply another `i32` parameter (a local). The interesting twist is signature strictness: Wasm validates that callee and caller types match, so the backend *pads* every `swiftcc`/`swifttailcc` function with the Swift-special parameters even when the IR omits them:

```cpp
// For swiftcc and swifttailcc, emit additional swiftself, swifterror, and
// (for swifttailcc) swiftasync arguments if there aren't. ... necessary to
// match callee and caller signature for indirect call.
if (!HasSwiftSelfArg)  { ... Flags.setSwiftSelf();  CLI.OutVals.push_back(DAG.getUNDEF(PtrVT)); }
if (!HasSwiftErrorArg) { ... Flags.setSwiftError(); ... }
if (CallConv == CallingConv::SwiftTail && !HasSwiftAsyncArg) { ... Flags.setSwiftAsync(); ... }
```
**[V]** ([WebAssemblyISelLowering.cpp](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/WebAssembly/WebAssemblyISelLowering.cpp)). The original swiftself/swifterror padding is [D76049](https://reviews.llvm.org/D76049) (kateinoigakukun, accepted 19 March 2020) **[V]**; the documented ABI in WebAssembly/tool-conventions states that `func foo(_ value: Int)` becomes `(param i32 i32 i32)` at the Wasm level and that when called from JS the missing trailing params are `undefined` → `0` **[V]** ([SwiftABI.md](https://github.com/WebAssembly/tool-conventions/blob/main/SwiftABI.md)). This padding recently *caused* a bug: async typed-throws calls were miscompiled on wasm32 because "the WebAssembly backend pads the `swiftself` and `swifterror` parameters, which left the indirect typed-error pointer and the `swiftself`/context slot at different LLVM-IR positions for Thin versus Thick async callers"; fixed by [swift#89715](https://github.com/swiftlang/swift/pull/89715) (merged 14 July 2026) so the trailing pair is always `[ind_error, swiftself]` **[V]**.

### 2c. Task allocator

Unchanged on Wasm: `swift_task_alloc` goes to `AsyncTask::Private.Allocator`, a `StackAllocator<SlabCapacity,…>` (bump allocator over slabs) whose slabs are obtained through `MallocFreeAllocator` (`malloc`/`free`) **[V]** ([TaskAlloc.cpp](https://github.com/swiftlang/swift/blob/main/stdlib/public/Concurrency/TaskAlloc.cpp), [TaskPrivate.h](https://github.com/swiftlang/swift/blob/main/stdlib/public/Concurrency/TaskPrivate.h), [StackAllocator.h](https://github.com/swiftlang/swift/blob/main/stdlib/public/runtime/StackAllocator.h)). On WASI, `malloc` is wasi-libc's dlmalloc in linear memory **[PK]**. Async frames therefore live on the heap, not the Wasm shadow stack — which is also why the frames can outlive the Wasm call that created them.

### 2d. Executors

**Default: cooperative executor.** The Wasm stdlib is built with `SWIFT_STDLIB_SINGLE_THREADED_CONCURRENCY=TRUE` and `SWIFT_THREADING_PACKAGE=none` **[V]** ([Runtime-WASI-wasm32.cmake](https://github.com/swiftlang/swift/blob/main/cmake/caches/Runtime-WASI-wasm32.cmake), [wasmstdlibhelpers.py](https://github.com/swiftlang/swift/blob/main/utils/swift_build_support/swift_build_support/helpers/wasmstdlibhelpers.py)). The book describes the default as a single-threaded cooperative executor that "exits immediately after all tasks are dispatched" and cannot yield to the host, suitable for WASI CLIs **[V]** ([book: concurrency](https://book.swiftwasm.org/getting-started/concurrency.html)). The modern implementation, `CooperativeExecutor.runUntil`, drains timer queues into the run queue, runs jobs synchronously, then *blocks* in `_sleep(seconds:nanoseconds:)` until the next deadline (non-Embedded builds) or breaks when the queue is empty **[V]** ([CooperativeExecutor.swift](https://github.com/swiftlang/swift/blob/main/stdlib/public/Concurrency/CooperativeExecutor.swift)). So `Task.sleep` works in a WASI command by literally sleeping the one thread.

**Browser: `JavaScriptEventLoop`.** Verified from source **[V]** ([JavaScriptEventLoop.swift](https://github.com/swiftwasm/JavaScriptKit/blob/main/Sources/JavaScriptEventLoop/JavaScriptEventLoop.swift), [+LegacyHooks.swift](https://github.com/swiftwasm/JavaScriptKit/blob/main/Sources/JavaScriptEventLoop/JavaScriptEventLoop+LegacyHooks.swift), [+ExecutorFactory.swift](https://github.com/swiftwasm/JavaScriptKit/blob/main/Sources/JavaScriptEventLoop/JavaScriptEventLoop+ExecutorFactory.swift)):

- `installGlobalExecutor()` branches on `#if (compiler(>=6.4) || (swift(>=6.3) && arch(wasm32))) && !hasFeature(Embedded)`: it calls `_Concurrency._createExecutors(factory: JavaScriptEventLoop.self)` (SPI `ExperimentalCustomExecutors`, from [swift#80266](https://github.com/swiftlang/swift/pull/80266) / the "Custom Main and Global Executors" pitch). Otherwise — including **Embedded Swift**, "because ExecutorImpl.swift is excluded from the embedded Concurrency library" — it uses `installByLegacyHook()`.
- The legacy path overwrites `swift_task_enqueueGlobal_hook`, `swift_task_enqueueGlobalWithDelay_hook`, `swift_task_enqueueGlobalWithDeadline_hook`, `swift_task_enqueueMainExecutor_hook`, and `swift_task_asyncMainDrainQueue_hook`.
- Scheduling: immediate jobs are queued via `promise.then { … }` on a pre-resolved `JSPromise` (i.e. a microtask; a `TODO(katei)` asks whether `queueMicrotask` would be faster), delayed jobs via `setTimeout(JSOneshotClosure, ms)`. Priorities are not modelled.
- Under `_runtime(_multithreaded)` there is one event loop per thread (TLS `swjs_thread_local_event_loop`); a job enqueued from a worker without executor preference is bounced to the main thread with `swjs_send_job_to_main_thread` → `postMessage`.
- Draining: the `MainExecutor.run()` implementation calls `swjs_unsafe_event_loop_yield()` "to skip the `exit(0)` call by `swift_task_asyncMainDrainQueueImpl`" — the stdlib really does `_exit(result: 0)` when `run()` returns **[V]** ([ExecutorImpl.swift](https://github.com/swiftlang/swift/blob/main/stdlib/public/Concurrency/ExecutorImpl.swift)). The JS side implements that import as `throw new UnsafeEventLoopYield()` — a JS exception that unwinds the entire Wasm stack back to `main()`'s JS caller, which catches and ignores it **[V]** ([Runtime/src/index.ts](https://github.com/swiftwasm/JavaScriptKit/blob/main/Runtime/src/index.ts)). This is a deliberate, cheap "stack switch" using JS exception propagation through Wasm frames.

Note on proposal status: the executor-factory API JavaScriptKit uses is still a pitch — "[Pitch 4] Custom Main and Global Executors" was posted 21 August 2026 and explicitly keeps the hook functions for Embedded Swift **[V]** ([forums 89107](https://forums.swift.org/t/pitch-4-custom-main-and-global-executors/89107)). I could not confirm an SE number for it (SE-0472 in your brief may be a different proposal) **[?]**.

**`WebWorkerTaskExecutor`.** A `TaskExecutor` (SE-0417 task-executor preference) that runs tasks on Web Workers sharing memory; requires `JavaScriptKit`, the `wasm32-unknown-wasip1-threads` target (an implementation of the withdrawn wasi-threads proposal, `pthread` API) and `SharedArrayBuffer` **[V]** ([book: multithreading](https://book.swiftwasm.org/getting-started/multithreading.html)). JS runtime `startThread` calls the module's `wasi_thread_start` export in the worker **[V]** (index.ts). The threads stdlib is built with `SWIFT_THREADING_PACKAGE=pthreads` and `-Xcc -matomics -Xcc -mbulk-memory -Xcc -mthread-model -Xcc posix -Xcc -pthread -Xcc -ftls-model=local-exec` **[V]** ([wasistdlib.py](https://github.com/swiftlang/swift/blob/main/utils/swift_build_support/swift_build_support/products/wasistdlib.py)).

**`JSPromise` bridging.** After installing the executor "you can await on the value property of JSPromise instances" **[V]** (book); `JSPromise.value`/`.result` in the same file bridge `then` callbacks to a Swift continuation **[V for existence; PK for `withCheckedThrowingContinuation` detail]**.

**Host-driven executors outside the browser.** The Patch SDK post (20 June 2026) shows the WASI-reactor-inside-an-iOS-app case: with no event loop "the job goes… nowhere"; they install `swift_task_enqueueGlobal_hook` to *capture* jobs and export a `pump(budget:)` that runs `swift_job_run` from the host, describing this hook as "unofficial but long-stable" with JavaScriptEventLoop as prior art **[V]** ([Medium post](https://jackappdev.medium.com/running-swift-async-await-inside-webassembly-where-there-is-no-event-loop-0f5df60dbb67)).

### 2e. `main` and the reactor model

JavaScriptKit refuses command-model modules: "JavaScriptKit supports only WASI reactor ABI. Please make sure you are building with: `-Xswiftc -Xclang-linker -Xswiftc -mexec-model=reactor`"; its `main()` calls `_initialize()` and then `__main_argc_argv(0, 0)` inside a `try/catch` that swallows `UnsafeEventLoopYield` **[V]** (index.ts). So the instance stays alive after `main` "returns" (actually: after the drain loop is aborted by the JS exception), and later microtasks/timeouts re-enter exported closures.

### 2f. JSPI / Asyncify

Because Swift's async is CPS-split, SwiftWasm needs neither JSPI nor Asyncify: suspension is "return to the executor", and the JS event loop resumes via exports **[V by construction from the sources above]**. I found no Asyncify use in current JavaScriptKit/toolchain code. A 2020 SwiftWasm blog update described using `wasm-opt --asyncify` "to unwind and rewind the module's call stack when we want to put Swift execution to sleep" (early Tokamak/carton experiments) **[?, secondary snippet; original post not fetched]**. Blocking primitives remain unsafe: `DispatchSemaphore.wait` "would almost certainly freeze the single-threaded wasm executable" **[V, from the swift-dispatch-async README snippet]** ([PassiveLogic/swift-dispatch-async](https://github.com/PassiveLogic/swift-dispatch-async)).

### 2g. Embedded Swift + concurrency

Embedded Swift on Wasm does support async: `test/embedded/concurrency-tailcall.swift` checks `swiftcc` vs `swifttailcc`/`return_call` for `-enable-experimental-feature Embedded` on `OS=wasip1` **[V]**. The executor must be supplied through the hook API (ExecutorImpl.swift is excluded from Embedded `_Concurrency`); JavaScriptKit 0.56.1 fixed the Embedded event loop where `clock.enqueue` is unavailable, and its `SchedulingExecutor.enqueue(after:)` has an `#if $Embedded` branch that only accepts `Duration`-based clocks **[V]** (source; [July 2026 update](https://forums.swift.org/t/swift-for-wasm-july-2026-updates/88673)). The embedded cooperative executor's timer branch is compiled out (`#if !$Embedded`), so timers need a host **[V]**. WasmKit 0.3.x now runs Embedded Swift in its core engine (ESP32-C6 example) **[V]**.

## 3. How Swift errors compile to Wasm

**`swifterror`.** LLVM's generic `TargetLowering::supportSwiftError()` returns `false` and the WebAssembly lowering does not override it (grep of `WebAssemblyISelLowering.{h,cpp}` finds no `supportSwiftError`) **[V]**, so the register-based optimisation is off: the `swifterror` argument is an ordinary pointer to a caller-owned error slot in linear memory, passed as the padded trailing `i32` described in §2b (D76049) **[V + inference]**. `throws` therefore costs one extra parameter plus a load/branch after each call — no unwinding, no EH tables. Typed throws use an indirect error pointer in the async entry (the position bug fixed by swift#89715) **[V]**.

**Traps.** `fatalError`/precondition failures end in `abort()`; wasi-libc's `abort()` is `__builtin_trap()` — "wasm doesn't support signals, so just trap to halt the program" — i.e. the `unreachable` instruction **[V]** ([wasi-libc abort.c](https://github.com/WebAssembly/wasi-libc/blob/main/libc-bottom-half/sources/abort.c)). Swift's `Builtin.int_trap` → `llvm.trap` → `unreachable` **[PK]**. A trap poisons the instance in browsers (the same "hard abort" behaviour Cloudflare describes for Rust; see §5).

**Wasm EH not required.** Nothing in the Swift-on-Wasm build passes `-fwasm-exceptions`; the runtime's C++ does not use exceptions (Swift's runtime is compiled with exceptions disabled) **[PK; I could not locate the exact `-fno-exceptions` line in `AddSwiftStdlib.cmake` today — ?]**. `setjmp/longjmp` is not used by the Swift runtime **[PK]**. Contrast: WasmKit (Swift's own interpreter) *implements* the exception-handling proposal as of 0.3.0 **[V]**.

## 4. Cancellation on SwiftWasm

Cancellation is the runtime's cooperative flag (`Task.isCancelled`, `checkCancellation`, `withTaskCancellationHandler`) — unchanged **[PK]**. The Wasm-specific angle is atomics: the single-threaded stdlib is built with `SWIFT_THREADING_PACKAGE=none` and `SWIFT_STDLIB_SINGLE_THREADED_CONCURRENCY` **[V]**, and LLVM's Wasm backend "automatically lowers atomic operations and TLS to nonatomic operations and non-TLS data when… the atomics or bulk-memory features are not present"; `-mthread-model posix` was replaced by `-matomics` as the source of truth, and the linker refuses to link such objects into a shared-memory module **[V]** ([D79542](https://reviews.llvm.org/D79542), [D58742](https://reviews.llvm.org/D58742), [D59625](https://reviews.llvm.org/D59625)). So the runtime's `std::atomic` status words compile to plain loads/stores in `wasm32-unknown-wasip1` and to real atomics only in the `-threads` stdlib.

## 5. Rust comparison

- **Async**: `async fn` → compiler-generated state machine polled by an executor **[PK]** ([async book](https://rust-lang.github.io/async-book/)). On `wasm32-unknown-unknown`, `wasm-bindgen-futures` now re-exports `js_sys::futures` (`spawn_local`, `JsFuture`, `future_to_promise`); the queue "Use[s] queueMicrotask to execute as soon as possible. If it does not exist fall back to the promise resolution" (`Promise::resolve(undefined).then`) **[V]** ([js-sys/src/futures/queue.rs](https://github.com/wasm-bindgen/wasm-bindgen/blob/main/crates/js-sys/src/futures/queue.rs)). New: a JSPI path — `jspi_block_on_promise` lets sync code "suspend the current promising execution until a JS `Promise` settles", implemented with a `#[wasm_bindgen(catch, suspending)]` import and `WebAssembly.promising`; modules that don't use it "keep running on engines without exnref/JSPI" **[V]** ([jspi.rs](https://github.com/wasm-bindgen/wasm-bindgen/blob/main/crates/js-sys/src/futures/jspi.rs)).
- **WASI**: `wstd` is a single-threaded WASI 0.2 runtime built on `poll` for `wasm32-wasip2` **[V]** ([docs.rs/wstd](https://docs.rs/wstd/latest/wstd/)). `wasm32-wasip3` was added as Tier 3 in [rust#147205](https://github.com/rust-lang/rust/pull/147205) (merged 7 Oct 2025, Rust 1.92), identical to wasip2 except `target_env = "p3"`; Tier-2 promotion proposed June 2026 ([compiler-team#1001](https://github.com/rust-lang/compiler-team/issues/1001)) **[V]**. WASIp3's native async lives in the component model, with `wit-bindgen` generating async bindings and Wasmtime host support (`wasmtime_wasi::p3`) **[V]** ([wasmtime p3 bindings](https://docs.wasmtime.dev/api/wasmtime_wasi/p3/bindings/index.html), [Fermyon "Looking ahead to WASIp3"](https://dev.to/fermyon/looking-ahead-to-wasip3-5aem)). Claims that WASI 0.3 "shipped February 2026 in Wasmtime 37+" come from low-quality aggregators **[?]**.
- **Panics**: `wasm32-unknown-unknown` defaults to `-Cpanic=abort` (→ `unreachable`); `exception-handling` is *not* a default feature; unwinding needs nightly `-Zbuild-std` with `RUSTFLAGS='-Cpanic=unwind -Cllvm-args=-wasm-use-legacy-eh=false'` **[V]** ([rustc platform docs](https://doc.rust-lang.org/rustc/platform-support/wasm32-unknown-unknown.html)). Tracking issue [#118168](https://github.com/rust-lang/rust/issues/118168): compiler and std support done, LLVM/new-EH, docs and stabilisation pending **[V]**. [#146457](https://github.com/rust-lang/rust/pull/147169) (Sept 2025) stops emitting EH instructions for `C-unwind` on Wasm targets without `+exception-handling` ([#140293](https://github.com/rust-lang/rust/issues/140293)) **[V]**. LLVM's `-wasm-use-legacy-eh` defaults to `true` since LLVM 20 (Jan 2025), "will later change to false" **[V]** ([llvm#122158](https://github.com/llvm/llvm-project/pull/122158)); Emscripten 4.0.0 (Jan 2025) added `-sWASM_LEGACY_EXCEPTIONS` (default true) **[V]** ([ChangeLog](https://github.com/emscripten-core/emscripten/blob/main/ChangeLog.md)). ## 6. Kotlin/Wasm

Kotlin/Wasm requires WasmGC and (for browsers) the *legacy* EH proposal; supported: Chrome 119+, Firefox 120+, Safari 18.2+ **[V]** ([wasm-overview](https://kotlinlang.org/docs/wasm-overview.html), [wasm-configuration](https://kotlinlang.org/docs/wasm-configuration.html)). ## 8. Go / TinyGo

The gc toolchain's `js/wasm` port owns its scheduler: `wasm_export_run` sets `SP` to `runtime·wasmStack` in linear memory, calls `rt0_go` then `wasm_pc_f_loop`; `wasm_export_resume` re-enters via `handleEvent`; `getsp` exposes the stack pointer to JS **[V]** ([rt0_js_wasm.s](https://github.com/golang/go/blob/master/src/runtime/rt0_js_wasm.s)); `wasm_exec.js` drives `resume()` from timeouts (`scheduleTimeoutEvent`) and wrapped funcs **[V]** ([wasm_exec.js](https://github.com/golang/go/blob/master/lib/wasm/wasm_exec.js)). `syscall/js.FuncOf`: "Invoking the wrapped Go function from JavaScript will pause the event loop and spawn a new goroutine… calling any async JavaScript API… will cause an immediate deadlock. Therefore a blocking function should explicitly start a new goroutine" **[V]** ([pkg.go.dev/syscall/js](https://pkg.go.dev/syscall/js)). On `wasip1`, "Wasm is a single threaded architecture", goroutines interleave but "any host function calls will cause all goroutines to block" **[V]** ([go.dev/blog/wasi](https://go.dev/blog/wasi)); Go 1.24 added `go:wasmexport` and `-buildmode=c-shared` reactor builds for wasip1 **[V]** ([go1.24 notes](https://go.dev/doc/go1.24)). ## 10. Lessons for a new language emitting Wasm

1. **CPS/coroutine-split async needs guaranteed tail calls or an explicit trampoline.** Swift chose CPS + `musttail`; on Wasm that meant three years of "call stack exhausted" bugs until `swifttailcc` reached LLVM in 2026, and it is still opt-in (`-mtail-call`) with an ABI split. If you can't require the `tail-call` feature (it's in Wasm 3.0 and all browsers/Wasmtime ≥22, but not in LLVM's `generic` CPU), emit a trampoline (return-to-driver) or a state-machine design like Rust/Kotlin/C# that never relies on tail calls.
2. **Make the calling-convention choice a single, global, ABI-visible decision.** Swift's `swiftcc` vs `swifttailcc` regimes differ in Wasm signatures; mixing requires separate stdlib builds. Decide up front and bake it into your target/feature string.
3. **Wasm signature strictness bites "extra-register" ABIs.** Anything you'd put in a dedicated register (async context, error slot, self) becomes an explicit parameter, and every function of that convention must carry it even when unused (LLVM pads with `undef`). Order those trailing parameters deterministically — Swift's typed-throws miscompile came from padding-dependent positions.
4. **Errors as values are the cheapest and most portable choice.** Swift's `swifterror`-as-pointer needs no EH proposal, no unwinder, and works on every engine; Kotlin/.NET/Rust-unwind pay for Wasm EH and must track legacy vs exnref defaults (LLVM/Emscripten still default to legacy). If you do use EH, use the *JS tag* trick for browser interop like Kotlin.
5. **Traps are terminal.** `abort()`/`unreachable` poisons the instance; provide a recoverable failure path (typed errors, or panic-to-exception at the boundary as Cloudflare did) before shipping to long-lived hosts.
6. **Design the executor as a pluggable driver from day one.** Every successful system here exposes a "run one job / enqueue job" hook (Swift's `swift_task_enqueueGlobal_hook`/`ExecutorFactory`, Go's `resume`, Rust's `spawn_local` queue, Kotlin's dispatchers) and lets the host (JS microtasks/`setTimeout`, a native pump, WASI `poll`) own liveness. Blocking waits on a single thread are fatal; sleeps must become timers.
7. **Use the reactor model and never let `main` "finish".** JavaScriptKit's `UnsafeEventLoopYield` — a JS exception thrown through Wasm frames to abort the drain loop — is a neat, zero-cost way to return control to the host; a cleaner design just makes `main` return after installing callbacks.
8. **Keep coroutine frames off the Wasm stack.** Slab-allocated task frames (Swift), heap futures (Rust), continuation objects (Kotlin) survive returning to the host; Wasm shadow-stack frames don't.
9. **Threads and atomics are a separate target, not a flag.** Non-atomic lowering without `+atomics` means one runtime build per threading model; plan for `wasip1-threads`/shared-everything as a distinct triple and expect the host (SharedArrayBuffer, cross-origin isolation) to constrain it.
10. **Only reach for JSPI/Asyncify for legacy synchronous APIs.** Swift needs neither; Rust's wasm-bindgen added JSPI only as an escape hatch for sync code and keeps it out of modules that don't use it.

**Unverified/open items to flag:** whether shipped Swift SDK stdlibs are built with tail calls (evidence says no); the exact `-fno-exceptions` line in Swift's runtime build; the SE number of the executor-factory proposal; NativeAOT-LLVM's EH mechanism; Firefox's exact tail-call version; any measured `return_call` overhead.
