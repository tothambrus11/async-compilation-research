# Compilation strategies for colorless async and effect-typed suspension

Research memo for the Ferlium designer (issue #18: "Building on our effect system, we want async support with colorless functions"). Target: Rust-hosted, HM-inferred, row-polymorphic effects (`read`, `write`, `fallible`), per-effect-row monomorphization, `fallible` already lowered to status-return + explicit cleanup CFG, MIR SSA → `wasm-encoder` WASM first, native later, embedded in Rust hosts and the Candli browser game engine.

Legend: **[V]** = verified this session against the cited source; **[PK]** = prior knowledge with a canonical URL, not re-fetched; **[?]** = could not verify, treat with caution.

---

## 0. Executive summary

1. There are exactly three ways to make suspension colorless: give every activation its own stack (stackful), rewrite functions that may suspend into resumable state machines/CPS (stackless, compiler-driven), or ask the engine to switch stacks for you (JSPI / stack switching / fibers). Everything in the literature is one of these or a hybrid.
2. For Ferlium, the closest existing system is **Koka's compilation of effect handlers to C** [V]: a *direct-style* calling convention in which every effectful call is followed by an `if (ctx->is_yielding) { yield_extend(join_point); return; }` check, with the continuation built lazily only when a real suspension happens, and a *type-selective* transform that leaves total functions untouched. That is structurally identical to what Ferlium already does for `fallible` — a status-return convention with an explicit cleanup CFG — which means the `fallible` lowering can be generalised into a `suspend` lowering rather than replaced.
3. The hard design questions are not the transform itself but (a) the ABI of first-class function values of unknown effect, (b) what a *dropped-mid-suspension* frame owes the compiler (drop glue for temporaries), and (c) who owns the continuation at the host boundary. On (c), the Godot / Lua / Unity model — the host holds an opaque "function state" handle and calls `resume(handle, value)` — is precisely what a CPS/state-machine-compiled guest can offer to a Rust or browser host with **no JSPI, no Asyncify, no engine support**.
4. Engine-level stack switching is real but not yet a portable baseline: JSPI is Phase 5 (standardised) and shipping in Chrome, but Firefox is behind a flag; the general Stack Switching (WasmFX) proposal is Phase 3 [V]. Do not make it the only path.

## 1. The colouring problem and the three escapes

Bob Nystrom's "What Color is Your Function?" (2015) sets five rules: every function has a colour; the way you call it depends on colour; a red (async) function can only be called from red; red is more painful to call; some core library functions are red. His stated cure is the thing Go, Lua and Ruby share: "multiple independent callstacks that can be switched between", which lets Go "eliminate the distinction between synchronous and asynchronous code" [V] (https://journal.stuffwithstuff.com/2015/02/01/what-color-is-your-function/).

An *effect-typed* language reframes this: suspension is still a property of a function, but it is **inferred and polymorphic** rather than declared and viral. `map : (a -> e b) -> [a] -> e [b]` is red or blue depending on `e`. The colour still exists in the *compiled artefact* — a suspending `map` cannot share machine code with a non-suspending one under any of the three strategies below — but it vanishes from the *source*. The whole question is who pays to reconcile the two.

### 1a. Stackful coroutines / green threads

- **Go**: goroutines start with ~2 KB stacks; each function prologue compares SP against `g.stackguard0` and calls `morestack`, which allocates a bigger contiguous stack and copies frames, adjusting interior pointers (contiguous stacks replaced segmented stacks in Go 1.4) [V] (https://groups.google.com/g/golang-dev/c/i7vORoJ3XIw, https://github.com/golang/go/issues/18138). Pointer adjustment requires precise stack maps — i.e. a GC-grade compiler.
- **Lua**: each coroutine is a separate `lua_State` with its own Lua stack; yielding across a C frame that was not entered with `lua_callk`/`lua_yieldk` is a hard error ("attempt to yield across a C-call boundary") because the C stack cannot be captured [V] (https://lua-users.org/lists/lua-l/2008-04/msg00148.html; manual [PK] https://www.lua.org/manual/5.4/manual.html#4.5). This is the canonical illustration that stackful coroutines in an *interpreter* are cheap, but crossing into the host's native stack breaks them.
- **Java Loom (JEP 444, final in JDK 21)**: virtual-thread stacks live in the heap as `StackChunk` objects; on blocking, the JVM "freezes" the stack by copying it from the carrier thread into the chunk and "thaws" it lazily on resume [V] (https://openjdk.org/jeps/444, https://foojay.io/today/the-basis-of-virtual-threads-continuations/). Loom is why Scala's Ox and Gears can do direct-style concurrency without any compiler transform [V] (https://ox.softwaremill.com/latest/basics/direct-style.html, https://ox.softwaremill.com/v0.3.7/compare-gears.html).
- **Zig, era 1 (≤0.9/0.10, removed in the self-hosted compiler)**: async was *inferred* — a function became async if it contained `suspend` or `await`ed an async frame; frames were **caller-allocated** with size `@Frame(func)`, obtained via `@frame()`, and function pointers had to be called via `@asyncCall` with an explicitly provided frame buffer because the calling convention differed [V] (https://ziglang.org/documentation/0.9.1/#Async-Functions, https://zig.guide/async/frames-suspend/). It was colorless in exactly the sense Ferlium wants (https://oleksii.shmalko.com/20211124040204/). Why it was dropped: per Loris Cro and Andrew Kelley, "async and await were deeply tied to language-level support for stackless coroutines", which forced one execution model on all code, and it could not be re-implemented in stage2 in time [V] (https://kristoff.it/blog/zig-new-async-io/, tracking issue https://github.com/ziglang/zig/issues/18873). The unsolved technical problems were frame size for recursion/indirect calls and the async calling convention leaking into every function pointer (see issue https://github.com/ziglang/zig/issues/5277, https://github.com/ziglang/zig/issues/8672) [V].
- **Zig, era 2 (0.16, `std.Io`, 2025–26)**: I/O is an injected interface passed like an `Allocator`; `io.async(f, args)` decouples call from return but does not promise concurrency (it may run synchronously); `io.concurrent` / `asyncConcurrent` demands real concurrency and fails with `error.ConcurrencyUnavailable`; `Future.await` and `Future.cancel` are idempotent and `cancel` is "your best friend, because it's going to prevent you from leaking the resource" [V] (https://andrewkelley.me/post/zig-new-async-io-text-version.html). Shipped implementation is `std.Io.Threaded`; io_uring/kqueue + **stackful** coroutine implementations exist as proofs of concept [V]. Stackless coroutines are deferred to a language feature: proposal #23446 adds `@asyncFrameSize`, `@asyncInit`, `@asyncResume`, `@asyncSuspend`, `@asyncFrame`, argued to have "broader support than stackful coroutines, because all of the suspend/resume machinery is lowered by the compiler to synchronous constructs" (WebAssembly, SPIR-V), and notes that one async function directly calling another "can actually be a tail call" [V] (https://github.com/ziglang/zig/issues/23446). The lesson for Ferlium: Zig's *new* colorlessness is dynamic dispatch on an `Io` vtable, and the compiler-level part is being rebuilt as caller-sized frames — the same design as era 1, but opt-in.

### 1b. Compiler-driven CPS / state machines

- **Kotlin `suspend`**: coloured but type-tracked. Every suspend function gets a hidden `Continuation<T>` parameter and returns `Any?`; if it suspends it returns the marker `COROUTINE_SUSPENDED`, otherwise the result directly. Suspension points in non-tail position generate a state machine (a `label` field, locals hoisted to fields, `resumeWith` re-entering at the label). **Tail-call optimisation**: a suspend function whose only suspension is a tail call to another suspend function gets *no* state machine — the continuation is just forwarded [V] (https://github.com/Kotlin/KEEP/blob/master/proposals/coroutines.md). Wrapping the tail call in `try/catch` defeats this [V] (https://doveletter.dev/articles/coroutines-compiler-machinery). `inline` functions are the escape hatch for higher-order code: "non-suspending inlined lambda parameters" may contain suspension points when the enclosing function is suspend, which is why `forEach`/`map` accept suspending lambdas without a suspend-flavoured overload [V] (https://kotlinlang.org/spec/asynchronous-programming-with-coroutines.html).
- **C#** `async` uses the same state-machine transform with an `IAsyncStateMachine` and `AsyncTaskMethodBuilder` [PK] (https://learn.microsoft.com/en-us/dotnet/csharp/asynchronous-programming/task-asynchronous-programming-model).
- **Rust**: `async fn` becomes a generator-like state machine implementing `Future::poll`. Rust deliberately rejected both green threads (RFC 230: unavoidable allocations, forced runtime, FFI/embedding cost — "switching code from executing on a green thread to running on the OS thread stack can be prohibitively expensive for FFI") and callback/CPS futures ("using a continuation passing style too often required allocating the callback"), choosing polling so that combinators compile "into a single state machine" in one perfectly sized allocation, with cancellation = drop [V] (https://without.boats/blog/why-async-rust/, https://aturon.github.io/blog/2016/09/07/futures-design/).
- **Swift**: async functions are split into *partial functions* that "run between each potential waiting point, always tail call the next part to run, wait by just returning"; each async frame is heap-allocated via `swift_task_alloc` with a size published by the callee (`sendToServer.frameSize`), fragments are chained with `musttail` under `swifttailcc`, and the chain of async contexts forms a logical task stack for tooling [V] (McCall & Schwaighofer, LLVM Dev Mtg 2021, https://llvm.org/devmtg/2021-11/slides/2021-AsyncFunctionsInSwift.pdf). SE-0296 states the async ABI is "radically different" and "necessarily less efficient" than the sync ABI [V] (https://github.com/swiftlang/swift-evolution/blob/main/proposals/0296-async-await.md).

### 1c. Engine-level stack switching

- **WebAssembly**: JSPI (JS Promise Integration) is **Phase 5 (standardised)**; Stack Switching (Francis McCabe & Sam Lindley, the WasmFX lineage) is **Phase 3** [V] (https://github.com/WebAssembly/proposals). JSPI is live in Chrome, behind a flag in Firefox; Safari withdrew its objection late 2025 [V] (https://webassembly.org/features/, https://github.com/web-platform-tests/interop/issues/1093). WasmFX adds `cont.new` / `suspend` (tagged) / `resume` as typed delimited continuations [V] (https://arxiv.org/pdf/2308.08347, https://wasmfx.dev/).
- **OCaml 5**: fibers are heap/malloc-allocated stacks that grow by reallocation; the compiler inserts stack-overflow checks in prologues (with a 16-word red zone so leaf functions can elide them), and reallocation walks the exception chain to fix absolute handler addresses [V] (https://github.com/ocaml-multicore/docs/blob/main/ocaml_5_design.md, https://arxiv.org/pdf/2104.00250).
- Scheme `call/cc` by stack copying and Lua coroutines are the interpreter-side cousins [PK].

## 2. Effect handlers as the general mechanism

| System | Continuations | Runtime representation | Multi-shot? |
|---|---|---|---|
| **OCaml 5** | one-shot, linear; `continue`/`discontinue` more than once raises `Continuation_already_resumed`; unhandled `perform` raises `Effect.Unhandled` | fiber = heap stack chunk; capture is a pointer grab, no copy [V] (https://ocaml.org/manual/5.4/effects.html, https://ocaml.org/manual/5.3/api/Effect.html) | No |
| **Koka** | multi-shot supported | evidence passing + yield bubbling + monadic translation to C; multi-shot "still requires a linear copy of the resumption stack segments" [V] (https://dl.acm.org/doi/10.1145/3473576) | Yes (cost: copy) |
| **Effekt** | one-shot in O(1), multi-shot by copying | capability passing; JS backend is a monadic runtime, LLVM backend via a "Machine" IR; ICFP 2025 paper "Multiple Resumptions and Local Mutable State, Directly" gives constant-time capture/resume for one-shot "while still supporting multiple resumptions by copying stacks when necessary" [V] (https://effekt-lang.org/evolution, https://dx.doi.org/10.1145/3747529) | Yes |
| **Flix** | multi-shot, deep, dynamically scoped handlers | JVM; **compilation strategy not verified** [?] (https://doc.flix.dev/effects-and-handlers.html, https://flix.dev/) | Yes |
| **Unison** | abilities, interpreted runtime | [PK] https://www.unison-lang.org/docs/fundamentals/abilities/ | Yes |
| **Haskell** | "Effect Handlers in Haskell, Evidently" (Xie & Leijen, Haskell 2020) is the library form of Koka's technique; `effectful`/`polysemy` are the mainstream libraries [PK] (https://dl.acm.org/doi/10.1145/3406088.3409022) | Library-dependent |

**Koka's async.** The design is Leijen's "Structured Asynchrony with Algebraic Effects" (TyDe 2017): async as a library of handlers with block-scoped interleaving, cancellation and timeouts [V] (https://dl.acm.org/doi/10.1145/3122975.3122977). Status in Koka 3: the libuv-based `std/async` branch has "TCP + UDP / file support" only and is blocked on type-system work; JS-backend async exists in community libraries [V] (https://github.com/koka-lang/koka/discussions/620). So "Koka async over libuv" is a design, not a shipped baseline — flag this.

**wasm_of_ocaml.** Two strategies, selected by flag: `--effects=cps` applies js_of_ocaml's CPS transform, which "is based on an analysis to detect parts of the code that cannot involve effects and keep it in direct style" (works well on monomorphic code, worse on heavy higher-order code); `--effects=double-translation` "keeps a direct-style version of the transformed functions in addition to the CPS version. The choice of running the CPS version is delayed to run time"; and wasm_of_ocaml **defaults to `--effects=jspi`**, requiring the GC, tail-call and exception-handling extensions [V] (https://ocsigen.org/js_of_ocaml/6.0.1/manual/effects, https://ocaml.org/p/js_of_ocaml-compiler/6.0.1/README_wasm_of_ocaml.html). This is the most directly relevant precedent for Ferlium: a mature compiler shipping *both* an engine-based and a transform-based lowering, with the transform's cost controlled by double translation.

**Scala** is going the other way: capture checking (experimental) tracks capabilities like `Async` at compile time; Gears (research, Project Caprese through 2028, JVM + Native) and Ox (JVM 21+) implement suspension with Loom — engine stack switching, not a compiler transform [V] (https://softwaremill.com/understanding-capture-checking-in-scala/, https://ox.softwaremill.com/v0.3.7/compare-gears.html).

**One-shot vs multi-shot** is the decisive cost axis. Async/await, generators, exceptions and cancellation are all one-shot. Only backtracking/nondeterminism needs multi-shot, and every system that supports it pays with stack copying. Ferlium should commit to **one-shot (linear) continuations**; that is what makes "cancellation = drop the frame" and "the frame owns its temporaries" well-defined.

## 3. The monomorphization approach in detail

**What Koka actually generates** (ICFP 2021, §2.10–2.11) [V]. After evidence passing and yield bubbling, the calculus is monadic (`Pure | Yield`), but the C backend erases the monad: "we always return results normally assuming Pure, and set a (thread-local) flag to indicate yielding (in which case the actual returned value is ignored). Moreover, every function has one extra parameter that holds the (thread-local) context ctx which contains the current evidence vector (ctx→w), and the yielding flag (ctx→is_yielding)." Generated code:

```c
int expr(unit_t u, context_t* ctx) {
  int x = perform_ask(ctx->w[0], unit, ctx);
  if (ctx->is_yielding) { yield_extend(&join2, ctx); return 0; }
  int y = perform_ask(ctx->w[0], unit, ctx);
  if (ctx->is_yielding) { yield_extend(alloc_closure_join1(x, ctx), ctx); return 0; }
  return x + y;
}
```

Key properties: (i) "the Koka compiler does a type-selective transformation and leaves out monadic binds for functions that are total (since those will never yield)"; (ii) the fast path along `Pure` "does no allocation ... and tail-recursive calls are preserved"; (iii) continuations are built lazily by pushing *join points* onto a resumption stack as the yield bubbles up (`yield_extend`), so a suspended frame costs a closure only at suspension time; (iv) `ctx->w[0]` uses a statically known evidence offset when the effect row is closed, and `find_ev(ctx->w, tag)` when the row is polymorphic; (v) "There is still an overhead in always needing to check after every effectful call if we are yielding or not ... this seems quite cheap on modern processors and the condition can be predicted well" (https://dl.acm.org/doi/10.1145/3473576; extended version https://xnning.github.io/papers/multip.pdf).

**Mapping onto Ferlium.** Ferlium's `fallible` lowering already is (i)–(ii): a status-return convention checked after each call, with an explicit cleanup CFG. A `suspend` (or `async`) effect can reuse the same skeleton with one addition: on a "suspended" status the caller must **spill its live locals into a heap continuation frame and push a resume-point** before returning the status upward. Two ways to do that spill:

- *Koka style (lazy, bubbling)*: at each check, allocate a join-point closure capturing live locals. Frames cost nothing until a real suspension; resumption re-enters the join point chain. Slightly slower after resume (join points aren't inlined).
- *Kotlin/Rust style (eager frame)*: the function's state machine frame is allocated/owned up front (by the caller, as in Zig 0.9 and Swift's `frameSize`, or by the task allocator); locals live in the frame; suspension is "store label, return". Constant per-call cost even when nothing suspends, but no allocation at suspension and trivial cancellation (drop the frame).

Because Ferlium monomorphizes per effect row, it can pick per instantiation: `map<e = {}>` is untouched direct style; `map<e = {suspend}>` gets the checks and spill code. This is exactly Kotlin's `inline` benefit obtained generally: Kotlin only gets suspend-ness "for free" inside inlined lambdas [V], whereas monomorphization gets it for every effect-polymorphic function.

**Code-size blowup.** Three multipliers to budget for: (1) one copy per distinct effect row per function (already paid for `fallible`); (2) within a suspending copy, the naive monadic translation duplicates the continuation at each bind — Koka's join-point sharing reduces "2^N to 2N" for N sequential effectful statements [V]; (3) Asyncify-style whole-program instrumentation, if used instead, costs roughly 50% code size and comparable slowdown, up to 5× on pathological inputs (SQLite), and drops to "almost zero" only with import whitelisting and `asyncify-ignore-indirect` [V] (https://kripken.github.io/blog/wasm/2019/07/16/asyncify.html). wasm_of_ocaml's double translation is the pragmatic middle: "some functions are compiled in several versions, and the choice of which version of the function to run is made at run time" [V].

**First-class function values of unknown effect — the real problem.** A closure of type `a -> e b` stored in a data structure has to have one ABI at the point of call. Precedents:

- *Kotlin*: `suspend () -> T` is a *distinct type* from `() -> T`; a suspending lambda is a `Function1<Continuation, Any?>` object; you cannot pass a suspend lambda where a plain one is expected, so the colour reappears at the function-type level [V] (KEEP).
- *Swift*: sync and async function types are distinct with "incompatible calling conventions"; the language allows implicit conversion sync→async by wrapping (thunk), never the reverse [V] (SE-0296).
- *Zig 0.9*: function pointers had a fixed calling convention; async ones had to be invoked via `@asyncCall(frame_buffer, ...)` [V].
- *Koka*: **one ABI for everything** — every function takes `ctx` and may set `is_yielding`; effect types only decide whether the *callee* gets checks/binds. A total function called through a polymorphic function value simply never sets the flag. Cost: the caller of an unknown-effect value always emits the check.
- *Rust*: `dyn Future` must be boxed (`Pin<Box<dyn Future>>`); `async fn` in traits stabilised in 1.75 but "did not include support for using traits containing async functions as `dyn Trait`", hence `async-trait`, `dynosaur` and the manual boxed-future idiom [V] (https://blog.rust-lang.org/2023/12/21/async-fn-rpit-in-traits/, https://debasishg.github.io/blog/pin-dyn/). This is the price of eager caller-sized frames: dynamic dispatch hides the frame size.

Recommendation for Ferlium: adopt Koka's uniform ABI *for function values whose effect row is open or contains `suspend`* — i.e. the `suspend`-instantiated ABI is "status-return + may-have-suspended", and a non-suspending closure is coercible into it by a thunk that never sets the flag (Swift's sync→async direction). Closed, `suspend`-free rows keep the plain ABI. That keeps monomorphic code zero-cost and makes higher-order/dynamic code pay one predictable branch per call rather than a boxing allocation. Frame size for dynamic callees is then not a problem, because Koka-style frames are allocated by the *callee* at suspension time, not sized by the caller.

## 4. Cancellation semantics compared

| System | Mechanism | What the compiler must provide |
|---|---|---|
| **Rust** | drop the `Future` → cancelled at whatever `await` it was parked on; "cancel-safety" is the resulting hazard (`tokio::select!` drops all losing futures and any state they own is lost); no async drop on stable — `AsyncDrop` is nightly-only (`#126482`), incomplete, with reported ICEs [V] (https://docs.rs/tokio/latest/tokio/macro.select.html, https://rfd.shared.oxide.computer/rfd/0400, https://doc.rust-lang.org/nightly/std/future/trait.AsyncDrop.html, https://github.com/rust-lang/rust/issues/140426) | Every suspended frame must be a value with complete synchronous drop glue for all live temporaries at every suspension point |
| **Swift** | cooperative flag: `Task.isCancelled`, `Task.checkCancellation()` throws `CancellationError`; cancelling "simply marks it as cancelled" [V] (https://swiftwithmajid.com/2025/02/11/task-cancellation-in-swift-concurrency/) | Nothing beyond ordinary error propagation |
| **Kotlin** | cooperative; every kotlinx suspending function checks at suspension and throws `CancellationException`; suspended coroutines are "resumed immediately with CancellationException"; `Job`/`coroutineScope` give structured concurrency [V] (https://kotlinlang.org/docs/coroutines-cancellation.html) | Exception must be deliverable *into* a parked continuation (`resumeWithException`) |
| **Go** | `context.Context` cooperative `Done()` channel [PK] (https://pkg.go.dev/context) | none |
| **C#** | `CancellationToken` cooperative, `OperationCanceledException` [PK] (https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads) | none |
| **OCaml Eio** | tree of cancellation contexts; "any operation that can switch fibers can also raise a `Cancelled` exception"; `Cancel.protect` for critical sections [V] (https://ocaml-multicore.github.io/eio/eio/Eio/Cancel/index.html) | Exceptions unwind the fiber stack normally |
| **Koka / Effekt** | a handler simply does not resume; `final ctl` marks never-resuming ops; `initially`/`finally` handlers and linear effects give cleanup guarantees [V] (https://koka-lang.github.io/koka/doc/book.html) | Non-resumed one-shot continuation must be finalised (Koka relies on the GC + `finally` clauses) |
| **Trio** | nurseries + cancel scopes; cancellation is an exception raised at checkpoints [V] (https://vorpus.org/blog/notes-on-structured-concurrency-or-go-statement-considered-harmful/) | none |
| **Zig std.Io** | `Future.cancel` requests cancellation; "the I/O implementation determines whether cancellation requests are honored" [V] | none |

**The principle.** With Ferlium's status-return `fallible`, three encodings are available and they differ only in *where the compiler must synthesise cleanup*:

1. **"Await returns a cancelled status"** (Kotlin/Eio style). The resume entry point accepts a status; on `Cancelled` the frame runs its existing `fallible` cleanup CFG from the suspension point and propagates. Requires that every suspension point be a *fallible* point too — a natural rule: `suspend ⊆ fallible` or, more precisely, the resume-with-error edge is added to the cleanup CFG that Ferlium already builds. Cheapest for Ferlium; cleanup code is reused; cancellation is observable and can be caught (`finally`-like).
2. **"Polled flag"** (Swift/Go). Purely library-level; needs nothing but a `read`-effect check. Weak: a frame parked on a host event is never resumed unless the host resumes it.
3. **"Drop the frame without resuming"** (Rust). Requires that a suspended frame be a self-contained value whose live temporaries have known drop glue at every suspension point — i.e. the state machine must expose per-state drop functions. This is the strongest guarantee (host can discard a script coroutine at any time) and the most demanding; Rust's still-missing `AsyncDrop` shows the residual gap (cleanup that itself needs to suspend).

Because Ferlium's frames will be *owned by the host* in the Candli scenario (§7), option 3's requirement — "drop(handle) is always safe" — must be met regardless. The pragmatic hybrid is **3 as the safety floor + 1 as the normal path**: the host may `drop`, but the polite API is `resume(handle, Cancelled)`, which runs user-visible cleanup through the existing fallible machinery.

## 5. Exceptions and panics through suspension

- **C++20 coroutines**: the body is wrapped in a try/catch that routes to `promise_type::unhandled_exception()`; the promise decides whether to stash an `exception_ptr` and rethrow at `co_await` or terminate; an exception escaping the promise's own hooks calls `std::terminate` [V] (https://devblogs.microsoft.com/oldnewthing/20210330-00/?p=105019, https://en.cppreference.com/cpp/coroutine/generator/promise_type/unhandled_exception). Unwinding *through* a suspended frame is impossible; the exception becomes a value inside the promise.
- **CPS'd programs**: identical conclusion — there is no stack to unwind, so errors are values threaded through continuations. Kotlin does this explicitly with `Continuation.resumeWith(Result)` / `resumeWithException` [V] (KEEP).
- **Rust**: a panic inside `poll` unwinds out of the executor's `poll` call; Tokio catches it per task and reports `JoinError::is_panic()` / `into_panic()`; users can `catch_unwind` or set `panic = "abort"` [V] (https://docs.rs/tokio/latest/tokio/task/struct.JoinError.html).
- **Koka**: exceptions are just an effect (`exn`), handled by a non-resuming handler; cleanup is via `finally` handlers, and the ICFP 2021 paper's `hexn` handler is the worked example [V].
- **OCaml 5**: exceptions unwind the current fiber; an unhandled `perform` raises `Effect.Unhandled` in the performer; `discontinue k exn` injects an exception into a suspended continuation — the same "resume with error" primitive as Kotlin [V] (https://ocaml.org/manual/5.3/api/Effect.html).

For Ferlium — which has no unwinding at all — the conclusion is clean: **panics abort** (as in WASM `unreachable`), **errors are statuses**, and a suspended frame is resumed with either a value or an error status. That is the one design where "exceptions" and "cancellation" are the same mechanism.

## 6. Generators: the minimal suspend effect

`yield` is the one-shot, synchronous, single-consumer special case of suspension:

- **Python** generators (PEP 255/342) are stackless frame objects resumed by `send()`; `throw()` injects an exception at the yield point [PK] (https://peps.python.org/pep-0342/).
- **C#** `IEnumerator` iterator blocks and Unity coroutines are the same state-machine transform as `async`, driven by `MoveNext()` [V for Unity] (https://docs.unity3d.com/Manual/Coroutines.html).
- **Kotlin** `sequence { yield(x) }` is a coroutine under `@RestrictsSuspension`, so the body "must ultimately invoke `SequenceScope.yield`" and cannot call arbitrary suspend functions — a static guarantee that the generator is synchronous [V] (KEEP).
- **Rust** `gen` blocks: RFC 3513 accepted, `gen` reserved in edition 2024, but still nightly-only under `gen_blocks` with open questions (self-referential generators, `Iterator` vs `IntoIterator`) [V] (https://rust-lang.github.io/rfcs/3513-gen-blocks.html, https://github.com/rust-lang/rust/issues/117078).

**Terminology, precisely.** A *coroutine frame* is the storage for a suspended activation. *Stackless* means the frame is not a machine stack: suspension can only happen in the coroutine's own body (not in callees, unless they are themselves coroutines), and the compiler decides frame layout. *Stackful* means the coroutine owns a real stack, so any callee at any depth may suspend, and the compiler needs nothing — but the runtime needs stack allocation, switching and (for native) pointer-safe growth. Swift's "partial functions", Kotlin's state machines, Rust futures, Zig-0.9 frames and Koka's bubbled join points are all stackless; Go, Loom, Lua, OCaml fibers and JSPI are stackful. An effect system lets a stackless design *look* stackful because the transform is applied transitively along the inferred `suspend` row — which is why Kotlin needs `inline` tricks and Ferlium does not.

For Ferlium, a `yield<a>` effect handled by an iterator adapter is the ideal first milestone: it exercises the whole suspend pipeline (frame spill, resume entry, drop-on-abandon) with no host or scheduler involvement.

## 7. Executors and the host boundary (the Candli scenario)

- **Lua hosts (Roblox/Luau, Defold, LÖVE)**: the engine owns the scheduler; scripts call `coroutine.yield()` / `task.wait()`, the engine stores the `lua_State*` and resumes it on the next Heartbeat or timer; `task.spawn` "communicates directly with the task scheduler and runs at 60hz"; Defold's idiom is `timer.delay(..., function() coroutine.resume(co) end)` around `coroutine.yield()` [V] (https://create.roblox.com/docs/reference/engine/libraries/coroutine, https://forum.defold.com/t/how-to-wait-in-defold/82203/5). The only rule the host must respect is Lua's C-boundary restriction.
- **Godot 4 GDScript**: any function containing `await` becomes a coroutine *transparently* — the user never annotates it. Implementation (verified in source): on `OPCODE_AWAIT` the VM copies its byte stack into a heap `GDScriptFunctionState` whose `CallState` holds `Vector<uint8_t> stack; int stack_size; int ip; int line; Variant result; Signal completed;`, connects to the awaited signal, and `GDScriptFunctionState::resume(const Variant&)` re-enters `GDScriptFunction::call` with the saved state; three stack slots that would create reference cycles are excluded and recreated on resume [V] (https://github.com/godotengine/godot/blob/master/modules/gdscript/gdscript_function.h, https://github.com/godotengine/godot/pull/61003). This is stack *copying* of an interpreter stack, not a compiler transform; its known costs are leaks/zombie states when the owning object dies before resumption [V] (https://github.com/godotengine/godot/issues/74449). Godot's user-facing colorlessness is therefore obtained at the cost of an opaque, host-held state object — the same shape a compiled Ferlium coroutine would expose.
- **Unity**: `IEnumerator` coroutines, `yield return null` resumes next frame after `Update`, `StopCoroutine` discards the enumerator [V] (https://docs.unity3d.com/Manual/Coroutines.html).
- **WASM guest without JSPI**: with a CPS/state-machine transform, a suspending export does not need the engine to hold anything. The pattern is: guest exports `call_f(args) -> status`, and on `Suspended` the guest has left a continuation handle (an index into a guest-side table, or a pointer into linear memory) plus a *reason* (which host event it waits on) in a well-known location; the host later calls `resume(handle, value_or_error_status) -> status`, repeating until `Done`. The guest's scheduler can be trivial (the host *is* the scheduler, as in Godot/Lua) or a guest-side run queue driven by a `tick()` export. This is exactly the "wait by just returning" half of Swift's partial-function model, with the host playing the role of the executor; it works identically for a Rust host calling a native Ferlium backend and for a browser host calling WASM through `wasm-bindgen`. Nothing in this design touches JSPI, Asyncify, or stack switching, so it runs in every engine today; if JSPI/stack switching is later available it can be used *only* to make a host→guest→host round trip look synchronous to legacy host code, without changing guest codegen.
- Alignment with Zig's new model is worth noting: Ferlium's host-provided `resume` driver is Zig's injected `Io` seen from the other side — the *host* chooses the execution model (frame-tick, event loop, threads) and the guest code is the same.

## 8. Design options for effect-typed colorless async in a monomorphizing WASM + native compiler

| Option | Guest codegen | WASM today | Native | Cancellation / drop | Host integration | Cost profile | Notes |
|---|---|---|---|---|---|---|---|
| **A. Stackful coroutines in linear memory + own scheduler (Go/Lua-style)** | none — but needs *stack switching in linear memory* | **Impossible in plain WASM**: the value stack is not addressable; would require Asyncify or stack switching | Feasible (ucontext/assembly, Go-like growth needs GC-grade stack maps or fixed-size stacks) | Cancel = discard stack; cleanup needs unwinding or per-frame drop tables | Host cannot hold a guest stack across its own frames without the C-boundary problem (Lua) | Zero transform cost; memory per coroutine | Rust rejected this for FFI/embedding reasons [V]; contradicts Ferlium's "no unwinding" |
| **B. JSPI / Stack Switching (engine)** | none; suspension = call an import that returns a Promise | JSPI Phase 5, Chrome yes, Firefox flag [V]; Stack Switching Phase 3 [V]; not in wasmtime/wasmer baselines yet | N/A — needs a separate native design anyway | Engine-level; guest frames are opaque; dropping a suspended stack is engine-defined | Only host→guest→JS Promise; a Rust host in the browser still crosses JS | Best runtime performance | wasm_of_ocaml's default [V]; portability gap; useless for the native backend |
| **C. Asyncify (Binaryen post-pass)** | none in Ferlium; post-process the `.wasm` | Works everywhere | N/A | Unwind/rewind only; abandoning a stack leaves no cleanup | Host calls `asyncify_start_rewind` etc. | ~50% size and speed, up to 5× worst case; near-zero with whitelists [V] | Instruments *every* function that may unwind — exactly the information Ferlium's effect rows already have, which is why doing it in the compiler is better |
| **D. CPS / state machine monomorphized on the effect row (Koka/Kotlin/Swift-style)** | Extend the `fallible` status-return lowering: after each `suspend`-row call, check status; on `Suspended`, spill live locals to a heap frame + push resume point; total/closed rows untouched | Works in every engine, no proposals needed | Same code, same ABI | **Frame is a value**: per-suspension-point drop glue (Rust) and/or `resume(handle, Cancelled)` through the existing cleanup CFG (Kotlin) | Host holds an opaque handle; `resume` export; host is the executor (Godot/Lua model) | Zero cost on non-suspending instantiations; one predictable branch per suspending call; lazy frame allocation (Koka) or eager frame (Rust) | First-class function values need a uniform "may-suspend" ABI for open rows (§3); code-size growth bounded by join-point sharing |
| **E. Hybrid: D as baseline, B as accelerator** | D | D everywhere; optionally use JSPI to present a blocking export to JS callers | D | D | D, plus a JSPI shim for legacy host APIs | D's cost, B's ergonomics where available | This is wasm_of_ocaml's `cps` vs `jspi` split [V] applied with the roles reversed (transform is the default) |

**Recommendation.** Option D, staged: (1) introduce a `suspend`-like effect (or a family: `yield<a>`, `async`) in the row system; (2) generalise the `fallible` status into a three-valued `Ok | Err | Suspended` return, reusing the cleanup CFG; (3) make suspended frames heap values with per-state drop functions so `drop(handle)` is always safe (Rust's guarantee, without Rust's `AsyncDrop` gap because Ferlium cleanup is synchronous); (4) expose `resume(handle, Ok(v) | Err(Cancelled))` to hosts; (5) give open/suspending function *values* one uniform ABI with sync→async thunking; (6) only then consider JSPI as an optional shim. The one thing to decide early is **one-shot only** — it is what makes (3) and (4) coherent, and it is what every async-oriented system in the survey (OCaml, Swift, Kotlin, Rust, Effekt's fast path) chose.
